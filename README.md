# IIOT PRD 工作台

**把一句话需求，变成三个能拿去开会的东西：一份「该不该做」的判断、一份能评审的 PRD、一个能点的原型。**

面向制造业中后台（QMS / LIMS / MES / SPC 这类），不面向纯互联网 C 端产品。

---

## 你在做需求分析时，它能替你干这些事

| 你手上正卡着的                     | 它给你的                                                    |
| --------------------------- | ------------------------------------------------------- |
| 拿到一句话需求（「来料检验要上系统」），不知道从哪问起 | 先问「现在怎么做的、谁在做、卡在哪一步」，把你的原话整理成一条**能拿去跟领导讲的判断**，而不是把方案当需求 |
| 场景想不全，尤其异常、权限、并发这些          | 按 11 个维度逐格扫，把「两个人同时点怎么办」「没权限的人看到什么」「数据没同步时显示什么」都摆出来     |
| 场景清单给业务看，他只说「漏了留样」          | 出一张**给他签的确认单**：这批场景全不全、P0 是不是这几条、有几个待确认要你拍              |
| 开发问「这个状态到底能不能改」，你去翻聊天记录     | PRD 里有**状态机表**：谁能从哪个状态到哪个状态、什么条件才允许，一行一行写死              |
| 评审会上被问「接口超时了呢」「有人重复提交呢」     | 12 类异常清单，每类写清怎么发现、用户看到什么、怎么降级、什么时候转人工                   |
| 说不清要多少人天、能不能拆期              | 把场景切成**能独立验收的片**，每片可以单独排期、单独上线                          |
| 业务方问「这事值不值得做」               | 一份判断：真问题是什么、有几种情况、P0 是哪几条，你可以直接拿去讲，也可以拿去否               |

## 你在做原型时，它能替你干这些事

| 你手上正卡着的                  | 它给你的                                    |
| ------------------------ | --------------------------------------- |
| 原型画完给业务看，他说「不是这个意思」      | **能点的原型**：按钮点下去状态真的变，弹窗里是要填的字段，当场就能试出分歧 |
| 原型发给别人，对方打不开（要装环境 / 连内网） | **单文件 HTML**，双击就开，微信发过去也能看              |
| 开发问「以文档为准还是以页面为准」        | 两者从**同一份契约**生成，对不上直接报错——你不用自己核          |
| 改了一个字段，不知道影响哪几页          | 契约里每个元素都带来源，改动会指出影响面                    |
| 交付时开发要一份能对着写代码的东西        | 契约里有命令、状态机、字段字典、切片，不含糊其辞                |

## 怎么用：说三句话

```
你：帮我分析一下这个需求：来料检验要在系统里做，现在靠纸单子……
    （附会议纪要 / 现有单据照片 / 旧系统截图都行）

它：扫完场景，给你一张确认单 —— 这批场景全不全、P0 是这几条对不对

你：签字确认

它：落流程、状态机、异常、评审，输出 PRD 与契约

你：画原型

它：出单文件原型（双击就开）+ 能导出的 PRD
```

**除签字外，中间不需要你操作任何命令。**

## 三个 skill 各管什么

| 段       | skill                    | 回答什么              | 你拿到什么                     |
| ------- | ------------------------ | ----------------- | ------------------------- |
| 01 业务分析 | `iiot-business-analysis` | 该不该做、谁在用、有多少种情况   | 真问题陈述 + 角色表 + 场景矩阵（要你签字）  |
| 02 需求分析 | `iiot-req-analysis`      | 系统怎么接：流程、状态、异常、验收 | **PRD 十节正文** + 契约（机器读的真相） |
| 03 原型设计 | `iiot-prototype`         | 长什么样、点得动吗、和文档对得上吗 | 单文件原型 + 页面标注 + 导出 PRD     |

01 是默认入口。只说「分析一下这个需求」就落到 01。

**动手前先判需求类型**：AI 型（要模型给判断）写模型节点与评测口径；非 AI 型（规则/表单/流程能闭环）跳过这两节，不会被套 AI 模板。

## 能力边界

### 它会做的

- 从原始材料（纪要、单据、截图、旧系统）里提取真问题，**区分「你以为的问题」和「你想要的方案」**
- 用十一维矩阵把场景扫一遍，含异常、边界、并发、权限这些最容易漏的
- 把 P0 场景落成流程、状态机、异常与验收标准，写成能评审的 PRD
- 出一份**单文件 HTML 原型**：双击就开、不装环境、按钮能点、状态会变
- 检查文档、契约、原型三者是否一致（不一致报错，不放过）

### 它不会做的

| 不做            | 原因                                  |
| ------------- | ----------------------------------- |
| 替你决定「这个需求做不做」 | 它给判断依据和风险清单，签字的人是你                  |
| 编数据、编排期、编用户量  | 没有就写【待确认】，宁可留空也不填假数                 |
| 替代真人评审        | 它组织四角色对抗评审，结论仍要业务方点头                |
| 直接生成可上线代码     | 输出是 PRD + 原型 + 契约，开发按契约实现           |
| 猜业务规则         | 拿不准就问，或标【待确认】列进待确认清单                |

### 已知的软肋

- 判据只能查**结构**（有没有这节、列齐不齐、编号对不对），查不了「这个业务判断对不对」
- 场景扫得全不全，最终还得你看那张确认单
- 非 AI 型需求若硬标成 AI 型，工具不拦（只会在评审时被问住）

## 你最终拿到什么

```
analysis/<产品名>/
├─ M1 ~ M6            工作底稿（内部用，评审不看）
├─ PRD.md             ★ 对外交付：十节正文，含权限矩阵 / 状态机 / 字段字典
├─ <产品>.proto.json   ★ 机器读的契约：命令、状态机、字段主档、切片
└─ dist/index.html    ★ 单文件原型，双击打开
```

`PRD.md` 里的功能表、状态机、权限矩阵、字段字典**全部来自契约**，不是两处各写一遍——所以文档和原型不会对不上。

## 它说「做完了」，你怎么验证

它不会跟你说「已完成，请查收」。你能验证的只有四件：

| 你能验证的                     | 怎么验                   |
| ------------------------- | --------------------- |
| 场景表要你签字，第 2 段才开工          | 你不签，它就停在那儿——随时能叫停     |
| 「做完」必须有个文件真的在那儿           | 不是嘴上说：产物不存在，它自己那关就过不去 |
| 每一步干了什么、为什么，都留在 `_run/` 里 | 交付后觉得不对劲，可以倒查是哪一步判断歪了 |
| 文档、契约、原型三者对不上会报错          | 你不用自己一条一条核            |

**除签字外没有需要你操作的环节**，但也别指望它替你做决定——签字那一栏永远空着等你。

## 常见问题

**只有一个模糊想法，能用吗？**  
能。第 1 段就干这个：从你的原话里找真问题，找不到会问你，不会替你编。

**做到一半发现上游结论错了？**  
说清改哪条。改了上游，下游契约与原型会标「需重做」，重做再重签。

**判据红了怎么办？**  
每条都写了该做什么。实在判断是误报，说一声——那是要修判据，不是要绕过它。

**非 AI 需求会不会被套 AI 模板？**  
不会。第 1 段先判类型，非 AI 型跳掉模型节点与评测集两节。

**能不能只用其中一段？**  
能。01 可单独用（只出业务分析），02 也能接已有的场景表。
