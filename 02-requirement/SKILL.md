### 执行留痕（每一步都要留，不是可选项）

`_state.json` 记**产物真相**（六步做到哪、谁签的字）；`_run/` 记**这一轮怎么干的**（目标原句、规划、每步意图）。两层不许合并，两个都不许手改——只经 `harness.py` 改。命令与字段以 `$SUITE/_design/HARNESS.md` §5 为准，本文不抄第二份。

两个词别混用：`step` 记的是一**步**，`plan` 里的一项是**子任务**（`B1`~`B4`）。一个子任务动辄十几步，**步数不等于进度**——别拿步数当勾数。

**① 对话可见：进度块贴进回复正文，不依赖任何界面**

用户要在对话里看见跑到哪了。**Task 工具在 skill 被调用时通常不显示**（依赖宿主 UI），所以进度的落点只能是文字：

1. 每次 `next` / `step` 之后，跑一次 `next --brief`，把返回的 3 行**原样贴进回复**，不概括、不省略：

```
── 1/3 ──────────────────────────────
A1 ✓  A2 ← 现在  A3
做 A2 角色 → M2-roles.md｜内含「角色表」 ｜ 账本 4 步
```

2. 开工贴一次、每完成一步再贴一次。用户看的是这个块，不是你的总结段落。
3. Task 工具（`TaskCreate`/`TaskUpdate`）能用就用，**不能用也不影响**——它是锦上添花，不是这套机制的落点。别因为它不显示就跳过进度块。
4. 块里的「← 现在」与「账本 N 步」是自检：`_run/` 推进了而块没变，就是你漏跑了 `next --brief`。
5. 进度块不是证据。做完没做完看产物文件与 `_state.json`；块只负责让人看见。

**② 开工前跑 `next`，这是固定初衷的唯一入口**

项目还没有 `_run/` 时先 `init --dir analysis/<产品>/ --goal "<目标原句>" --auto --stage 2`；之后每次会话第一件事、以及每完成一个子任务之后，都跑一次 `next --dir analysis/<产品>/`。它打目标原句 + 当前位置 + 下一步 + 三条约束。不许凭记忆说"上次做到 B3"——`--status` 管判据，`next` 管目标和链路，谁也替不了谁。

**③ 每完成一个有产出的动作，跑 `step`**

| 算一步 | 不算一步 |
|---|---|
| 读一份上游产物并**得出结论**、写或改了一个产物文件、跑了一次校验并**解释了结果**、开了一次评审 | 纯检索、grep 找位置、翻目录、再跑一遍 `--status` |

`--intent` 写**判断**不写动作：「确认让步与退货共用 verify 命令，四眼只差 actor 交集这一处」，而不是「读了 M4 参考」。将来复盘全靠这一列。
`--tool` / `--args` 必填（填你真跑的那个工具和关键参数，它同时是循环检测的依据），`--verdict` 默认 `ok`；产物不满足 `doneWhen` 记 `fail`；做了本段不该做的事（比如替 03 写 `ui.kind`）记 `drift`。

子任务要标完成，**四样一起给，缺一样就等于没给**：`--done --taskId B2 --out M5-exceptions.md`，且 `M5-exceptions.md` 必须真的存在、`doneWhen.contains` 里的串（如「异常清单」）必须真的出现。缺文件或缺串都 exit 6，但那是**防呆**，不是验收——验收仍是 `check_analysis.py` 那 21 条加 `check_contract`。只给 `--taskId` 也会 exit 6，那不是"工具不好用"，是这步还没做完。

**④ 每积累 2 步做一次里程碑自检**

`milestoneEvery` 到了就跑 `milestone --gap "..."`。`--gap` 写**这一轮产出对顶层目标还差什么**，"暂无""已对齐"算空话，判 exit 3、不计自检。自检只回答"偏没偏"，**不回答"完没完"**——它不给任何子任务打勾，别指望跑它把 B3 标完。本段的真例子：

> M4 只写了让步接收的主路径，M5 对退货复检的降级还是空的，M6 五条风险一条也没挂到切片批次上——差一个能签收的契约。

**⑤ 跳步、偏离、循环，三种动作**

| 情况 | 退出码 | 动作 |
|---|---|---|
| 遗忘（跳步） | 4 | 读 `next` 的注入块，回到它说的那步，**不要重开** |
| 偏离（意图与目标不沾） | 0 / 3 | 单次只记 `goalAligned:false` 并 WARN、**放行**（真实发现常常一开始看着不沾），第 2 次仍放行，**第 3 次**才判偏离 exit 3；那时停手，把当前动作和目标原句各念一遍。真要加步骤 → `amend --add ... --why ... [--stage N] [--done-file <产物>]`，对不齐目标会被硬拒；没给 `--done-file` 的新步骤，完成时只认 `--out` 指向的文件存在 |
| 循环（同一动作第 3 次） | 2 | **立刻停**，不许换措辞重试。读 `log --tail 10`，判断是工具用错还是这步本来就做不了，写进 `blocked` 交给用户 |

**禁令**：`blocked` 之后不许自己 `--force-unblock`，必须用户确认过才能解。死循环之所以发生，就是因为模型相信"再试一次就对"。

## 三、落契约的六条硬线

契约是这一段唯一的下游接口，写歪一条，03 全部白做。

| # | 硬线 | 怎么写 | 谁判红 |
|---|---|---|---|
| 1 | **一个动作 = 一个状态 = 一条命令** | 待排查／待分析／待下发／措施执行中／待验证／待审批，各自一条 `capability`，各自带 `actor` | `L2-54`~`L2-58` |
| 2 | **状态机端点不许悬空** | 每条 `from`/`to` 都能在状态集里找到；非终态必须有出向命令，否则单据永久卡住 | `L2-57`、状态机端点 |
| 3 | **四眼原则** | `stage` 为 `submit` 与 `verify` 的命令，`actor` 交集必须为空；要一人多角色必须显式 `sameActorOk` | 四眼判据 |
| 4 | **EARS 六字段一个不能省，且必须有非法路径** | 角色（岗位不用人名）/ 触发 / 规则 / 状态机 / 预期（单一响应）/ 验收（≥1 条 `kind:"illegal"`：状态不符、权限不足、并发冲突） | `L2-34` |
| 5 | **字段主档只登记被人点名过的字段** | M1/M3/M5 里出现过的业务字段才进 `fieldCatalog`，`dataSources` 要能解析到源表 | 字段主档与取数链路 |
| 6 | **切片要能独立验收** | 每批有范围、有依赖、无成环；一次做完必然后几页糊 | `P-01`~`P-11` |

| 键 | 归属 | 理由 |

| `capabilities[].ui`（`kind` / `entry` / `title` / `fields`） | 03 | 判定的是"这个动作用什么界面承载"，属渲染决策（`L2-55` 归 03） |
| `pages[].componentTree`、`pages[].prd`、`pages[].interactions` | 03 | 本段只给页面**骨架**：`id` / `moduleId` / `target` / `route` / `title` / `layout` / `entity` |

### M4 必须有「P1 未上流程」专节

这是上一轮最容易漏的地方：01 只把 P0 交给本段，P1 场景就会在这里**静默消失**——不报错、没人问、上线才发现缺一块。

规矩：**允许不上流程，不许没有下落。** 每个 P1 场景只有两条去向，二选一：

| 去向 | 写在哪 | 要写什么 |
|---|---|---|
| 进流程 | `M4` 的流程或分支 | 正常写，不用额外解释 |
| 后置 | `M4` 的「P1 未上流程」专节，**或** `M6` 结论里的后置批次 | 为什么不在这批 + 落到哪一步兜底 |

```markdown
## P1 未上流程

| 场景 | 为什么不在这批 | 落到哪一步兜底 |
|---|---|---|
| S-11 退货复检 | 频次 2 次/月，本批只做日频 | 走线下纸质单，M5 异常 7 记录补录 |
| S-14 跨厂调拨检验 | 涉及另一套系统，二期 | 本批不做，M6 风险 3 已登记 |
```

三条自检：

1. 状态变化写成「提交后状态更新」——空话，`A-30` 直接红。要写成「待取样 → 已取样」。
2. 评审写成「建议加强权限校验」——含"建议/优化/提升/加强"且没有问号，`A-52` 直接红。
3. 六份 md 里写出 `componentTree`、`interactions`、`ui.kind`、`pages[].prd`——`A-63` 红（**它只扫 md，不扫 proto**）。
4. proto 里替 03 写页面结构——`A-67` 红（顶层键与 `pages[]` 项走白名单）。这两条各管一头：`A-63` 管文档措辞，`A-67` 管契约结构，谁也替不了谁。
5. **`A-67` 的时点基准是 `--seal`**。签收那一刻契约是干净的；03 之后追加渲染键只会让它变 WARN，不会变红。要恢复严格判定：清干净后重签（`--stage 2 --seal`）。
6. **交付 02 必须签收**：`--stage 2 --seal` 全绿才落盘，有 ERROR 会被拒绝——**能带病签收的签收等于没有签收**。
7. **回改需求时，契约要重出，不要就地改**：从语义骨架重新生成，天然不带渲染键。在含渲染键的文件上改，就得手工删二十几个键，没人会做对——这也是 `A-67` 那条聚合 ERROR 想让你别走的路。

**`A-63` 的边界（别照着错的用例去扩词表）**：

```
反例（应放行）：M4 写「页面组件树与交互由第 3 段补」        → ERROR=0
正例（应红）：  M4 写「componentTree 按状态拆三块」          → A-63 ERROR
说明：判据只认结构键名。中文提到渲染层是正常交接，不判。
```

判据该判的是**有没有把渲染层结构写进来**，不是**有没有提到渲染层的词**。词表里每加一个中文词，就得能举出一个「正确但会被误伤」的句子——举不出来，就别加。完整案例见 `$SUITE/shared/references/09-pitfalls.md` 案例 3。
