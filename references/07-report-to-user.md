# 三个卡点怎么说人话

> A1 / A2 / A3 不是给产品经理看的，是给**业务方**看的。
> 他们不关心「契约」「切片」「状态机」，只关心三件事：**要我解决什么、要我拍什么板、什么时候能看到东西**。
> 这一章就是这三段的写法。写不好，前面六步再扎实也会被一句「你先做出来我看看」推回去。

---

## 1 先说结论：三段各自只回答一个问题

| 卡点 | 业务方脑子里的问题 | 你要给的答案 | 常见跑偏 |
|---|---|---|---|
| **A1 真问题** | 「你到底想让我承认什么？」 | 现在**卡在哪、损失多少**，以及「不做什么」 | 讲方案、讲页面、讲要开发什么 |
| **A2 对抗评审** | 「有什么风险？要我担什么责？」 | 只剩几条**只有你能定**的事 | 把 48 个问题全倒出来 |
| **A3 分批交付** | 「多久能看到东西？先做哪块？」 | 第一批能让你干什么，什么时候能看 | 讲技术切分、讲依赖关系 |

一句话检验：**把这三段发给一个没做过需求的车间主任，他能不能转述给厂长？** 不能就是没写好。

## 2 A1：真问题，用「损失」开场，不用「功能」开场

### 模板（照抄，填空）

```markdown
### A1 我们要解决的到底是什么（02-problem.md）

**一句话**：{现在的状态 + 量化损失}。
　　例：事故从发生到关闭平均 21 天，其中 9.4 天是「等某个人做他那一步」——不是活儿多，是没人知道该谁了。

**为什么会这样**：{用业务语言说机制，不写技术}
　　例：五道环节（排查 → 5why → 临时措施 → 预防措施 → 效果验证）分散在 6 张 Excel 里，
　　　　谁手上有哪一单、卡了几天，只存在人的记忆和微信群里。

**所以这次要做的不是**「{最常见的错误解法}」，**而是**「{真正要改变的一件事}」。
　　例：不是「把 Excel 搬到网页上」，而是「每一步自动变成某个人的待办」。

**我替你排除了 {N} 条路**（每条都写了为什么不做）：
1. {替代方案 1} —— {一句话说清它治不了什么}
2. {替代方案 2，最好有一条"不改系统、改组织"的}

**需要你拍板一件事**：{一个封闭问题}。
```

### 三条硬规则

1. **第一句必须带数字。** 「效率低」不是问题，「21 天里有 9.4 天在等人」才是问题。没有数字就用「一天几次 / 一次几分钟」现算一个，标上 `inferred`（我推的）。
2. **替代路径要写"它治不了什么"，不是"它不好"。** 业务方对"不好"很敏感，对"治不了什么"才会认真比较。
3. **结尾只问一个封闭问题。** 「你认不认这个方向」而不是「你觉得怎么样」——后者会换来一顿发散的意见。

### 不要出现

- 页面名、字段名、组件名（A1 阶段还没有页面）
- 「闭环」「赋能」「抓手」「沉淀」「打通」这类词，一个月后没人记得指什么
- 三条以上的问题（一次只让他做一个决定）

## 3 A2：对抗评审，只把「只有他能定」的捞出来

48 个问题里，绝大多数你能自己答。**只把口径冲突和取舍摆上来**，其余用一句话交代已经处理了。

### 模板

```markdown
### A2 有人会挑刺，这几条我挑不了，得你定（07-review.md）

我把研发 / 测试 / 业务 / 现场操作工四个角度过了 {48} 个疑问。绝大多数有答案，
剩 {2} 条是**公司内部口径不一致**，我定不了：

1. **{冲突点}**：{A 文档说 X}，{B 文档说 Y}。两条路都走得通，但只能选一条。
　 → 选 X：{后果}；选 Y：{后果}。
2. **{取舍点}**：{现在的做法} 会带来 {代价}。要不要为了 {收益} 接受它？

另外 {3} 条风险已经按「上线后多久会爆」排好，处理办法写进文档了，不用你现在看：
{一句话列名字即可}

**需要你拍板**：上面 1、2 各选一个。
```

### 三个判断：什么该往上报

| 该报 | 不该报 |
|---|---|
| 两份公司文件互相矛盾（谁对谁错只有甲方知道） | 「这个字段要不要必填」（你能定） |
| 涉及组织动作（设岗、改流程、谁签字） | 「按钮放左边还是右边」 |
| 会和已有系统/习惯冲突（要不要多扫一次码） | 「接口用什么协议」 |
| 需要花钱或改合同的 | 「表格分页 20 还是 50」 |

**报上去的条数 ≤ 3 条。** 超过 3 条，说明你在把判断工作推给业务方——那不是澄清，是甩锅。

## 4 A3：分批交付，别说「切片」

「切片」是工程内部词，业务方第一反应是数据分析或图片处理。统一改叫**「第几批」**。

### 模板

```markdown
### A3 怎么分批做（每一批交付后你就能用）

一次做完 {7} 页 {19} 个操作，结果一定是前几页精细、后几页糊。
所以我按「**每一批都能单独验收**」切成 {4} 批：

| 批次 | 这一批做完，谁能干什么 | 页面 | 包含的操作 |
|---|---|---|---|
| 第 1 批 | {安全员} 能把事故登进系统，{质量经理} 能确认或退回 | 新建 / 台账 / 详情 | 建单、确认、退回、关闭审批、驳回、导出 |
| 第 2 批 | {责任人} 打开就能看到「轮到我做的」 | 我的待办 | 发布、排查、5why、生成临时/预防措施、效果验证 |
| … | | | |

**建议先做第 1 批**，{时间} 后你能看到「事故终于有地方记了、卡了几天看得见」。

另外 {3} 件事我按默认值定了，你不反对就这么执行（改起来要返工，所以现在说）：
- {默认值 1}：{取值} —— {为什么这么定，来源是哪}
- {默认值 2}：…
- {默认值 3}：…

**需要你拍板**：第 1 批的范围认不认？认了我就开始画页面。
```

### 为什么这么写

- **"谁能干什么"比"包含哪些功能"更有说服力。** 业务方判断价值的方式是「我的人少干哪一步」，不是「你做了几个模块」。
- **默认值单独列一段，并写清"现在说还来得及"。** 不列默认值，评审时会被问「你怎么知道我车间叫 01~05」；列了不写成本，他也不会认真看。
- **只推销第一批。** 后面几批是给你自己排期的，业务方只需要认第一批——认了第一批，后面自然滚起来。

### 不许出现

- 「切片」「slice」「依赖成环」「P-05 上限 4 页」这类内部编号
- 「整体架构」「技术方案」「数据模型」
- 一次让他确认全部四批（他没这个耐心，也没这个必要）

## 5 术语对照：说之前先换一遍词

| 你脑子里的词 | 说给他听的词 | 为什么 |
|---|---|---|
| 切片 / slice | **分批交付 / 第 1 批** | 会被理解成数据分析或图片裁切 |
| 命令 / capability | **一个操作**（或直接说按钮名） | "命令"在车间语境里是设备指令 |
| 状态机 / stateMachine | **单据状态流转** | 说"这张单子会经过哪几个状态" |
| 契约 / proto.json | **需求清单**（能自动检查的那种） | 业务方听到 JSON 就停止思考了 |
| EARS / 需求句式 | **这条需求怎么验收** | 只讲结果，不讲方法论名字 |
| 承载形式 dialog / drawer | **弹框 / 抽屉 / 独立页** | 直接说长什么样 |
| 四眼原则 | **提交的人不能同时是审核的人** | 说原则名等于没说 |
| 锚点 nodeId | **这条意见标在哪个位置** | |
| 判据 / 造红验证 | **检查项 / 故意弄错看它报不报** | |
| 非目标 / out of scope | **这次不做什么** | |
| 量级 / 数据量 | **一年多少条、一天多少人用** | |

原则：**能换成日常说法就换；换不掉的，第一次出现时加一句括号解释**，之后可以继续用专业词——因为那时它已经有定义了。

## 6 三条通用写法（三段都适用）

1. **第一行就是结论。** 业务方只看前三行，剩下的在开会时才会被翻到。
2. **每个"我替你决定"的，都要写默认值 + 依据 + 改的成本。** 只写结论，等于把风险藏起来。
3. **每段结尾只有一个动作请求，且是封闭的。** 「认不认」「选 A 还是 B」——不要「你看看还有没有补充」。

## 7 自检清单（发出去之前过一遍）

- [ ] 三段各自的第一句话，能不能直接转述给厂长？
- [ ] A1 第一句带数字了吗？数字标了 `stated/inferred/measured` 吗？
- [ ] A1 有没有出现页面、字段、组件？（出现了就是方案，不是问题）
- [ ] A2 上报的条数 ≤ 3 吗？超了是不是在甩锅？
- [ ] A3 里还有没有「切片」两个字？
- [ ] 三个卡点加起来，一共让业务方拍几个板？（理想是 3 个，最多 5 个）
- [ ] 有没有把内部编号（P-05、L2-61、C-09）写进给业务方的段落？有就删掉。
