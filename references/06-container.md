# 容器工程：三栏壳、渲染引擎与迭代闭环

> 容器不是"给原型加个外壳"，它是把 `proto.json` 变成可评审界面的**运行时**。原型和 PRD 都从同一份数据渲染——所以改需求只改 JSON，不改 HTML，不会出现"文档和界面对不上"。

## 1 四层结构

```
assets/container/src/
├─ vue.global.prod.js   ① 运行时   Vue 3.4.38 全量 prod，143KB，内联
├─ runtime.js           ① 兜底     MiniVue shim，Vue 缺失时降级不白屏
├─ components.js        ② 组件库   51 个组件，options API + h()
├─ app.js               ③ 容器壳   三栏、状态机消费、标注、导出
├─ styles.css           ④ 样式     设计令牌 + 布局 + 组件样式
└─ build.py             ⑤ 打包     把 ①~④ + proto.json 内联成单文件
```

依赖方向是单向的：`components.js` 只吃 `props`，不认识 `store`；`app.js` 认识 `store` 和 `DATA`。这样组件可以直接搬进 `.vue` 文件给前端用，不用连带搬容器。

## 2 构建

```bash
cd assets/container/src
python3 build.py --proto ../../../examples/example-01-qms-incoming.proto.json \
                 --out ../dist/index.html
```

产物 `dist/index.html` 约 250KB（Vue 143 + 组件与样式 80 + 数据 25），双击即开、离线可用、可直接发微信。

三个构建期的检查（放在 `build.py` 里，越早越好）：

| 检查 | 为什么 |
|---|---|
| 组件/应用代码里不能出现 `</script` | 内联进 `<script>` 会提前闭合标签，整页白屏且报错指向不明 |
| proto 必须能被 `json.load` | 手改 JSON 多一个逗号就整页白屏，构建期拦住比运行时好 |
| 组件 `type` 必须在 `catalog.json` 白名单内 | 未登记组件在运行时降级成虚线框，构建期就该报出来 |

## 3 三栏布局：覆盖层，不挤压

```
┌───────────────────────────────────────────────┐
│ 容器条：目录 · 页面态 · 单据状态 · 标注 · PRD · 导出 │
├───────────────────────────────────────────────┤
│ ┌────────┐                        ┌──────────┐│
│ │ 目录   │      原型画布 1:1       │  PRD     ││  ← 两者都是浮层
│ │ 264px  │   宽 = 容器宽，不缩放    │ 360~760  ││     压在画布上
│ └────────┘                        └──────────┘│
└───────────────────────────────────────────────┘
```

三条硬约束：

1. **画布宽恒等于容器宽**。目录和 PRD 都是 `position: absolute`，不参与布局，所以展开前后 `stage.offsetWidth` 完全相等。这是"不被挤压"的硬证据，可用 `#test=1` 自检：

   ```bash
   chrome --headless --dump-dom "index.html#test=1" | grep -o '<div id="selftest">[^<]*'
   # {"canvasClosed":1440,"canvasOpen":1440,"notSqueezed":true,...}
   ```

2. **不缩放**。原型就是真实像素，1440 打开就是 1440。早期版本用过 `transform: scale` 适配，代价是：交给开发后前端要反算像素，而且 `getBoundingClientRect` 被缩放磨平，判据会假绿。要看全貌就收起浮层。

3. **PRD 浮层可拖宽 360~760**。拖的是浮层自身宽度，与画布无关。窄于 360 时表格挤成一列，宽于 760 就盖住大半个原型。

## 4 渲染引擎：JSON → UI

核心是 30 行的递归：

```js
function renderNode(node, ctx) {
  var comp = REGISTRY[node.type] || Fallback;         // 未登记组件降级，不白屏
  return h(comp, { key: node.id, p: node.props, n: node, ctx: ctx },
           (node.children || []).map(function (c) { return renderNode(c, ctx); }));
}
```

四个设计要点：

| 要点 | 做法 | 为什么 |
|---|---|---|
| 未登记组件降级 | `Fallback` 渲染虚线框 + 类型名 | 白屏无法定位；虚线框一眼看出哪个漏了 |
| 节点 `id` 作 `key` | `key: node.id` | `id` 分配后不改，diff 稳定，标注锚点也不跑 |
| 只认 `props` 不认全局 | 组件签名 `props: { p, n, ctx }` | 组件可独立搬走 |
| 表格列宽必填 | `table-layout: fixed` + 每列 width | 缺宽度的列在 fixed 下宽度为 0，表现为"列神秘消失" |

## 5 状态：三层，不混

这是整个容器最容易做错的地方。三种"状态"混在一起，按钮可用性就写不出来：

| 层 | 载体 | 例子 | 谁改 |
|---|---|---|---|
| **页面态** | `store.pageState` | default / loading / empty / zero-result / error | 顶部工具条切换（模拟） |
| **业务态** | `store.entityStatus` | created / sampled / reported / approved | 顶部「单据状态」切换；真实系统里由后端返回 |
| **组件态** | 组件内部 | 下拉展开、输入框聚焦 | 组件自己 |

业务态驱动命令可用性，逻辑集中在一个函数里。**角色和状态是两回事，判定结果也分两种**：

```js
// RD.can(capId, rowState, actor)
//   第三参不传 = 不校验角色（老调用、导出钩子、插件都只传两个参数）
if (who && allowed.length && allowed.indexOf(who) < 0)
  return { ok: false, denied: 'role',  reason: '当前角色「责任部门主管」不能做这个操作（仅 厂长 可用）' };
if ((cap.from || []).length && cap.from.indexOf(curKey) < 0)
  return { ok: false, denied: 'state', reason: (cap.reason || '当前状态不可用') + '（当前为「已归档」）' };
```

- `denied: 'role'` → **按钮不画**。画出来再置灰，等于告诉执行人"这里有个你不能碰的东西"，评审时会被反复问"为什么我不能点"。
- `denied: 'state'` → **按钮在，但灰着**，点一下给理由。

**提示文案是拼出来的，不是写死的。** 契约里只写「仅「待审核」可审核」，容器补上「（当前为「已归档」）」——否则每加一个状态，就要为每个命令补一句文案。

组件侧只写 `props.capability = "cap-approve"`，**禁止 `disabled: true`**。写了 `disabled` 就绕过了状态机，等于在组件上写死了一个业务规则。

**所有命令按钮都挂 `data-cap="cap-xxx"`**。R 层按它找元素，不按文字找——同名按钮（台账「审核」与顶栏「审核」）按文字一定会找错，改文案又会假红。

## 6 标注：锚点而不是坐标

```json
{ "id":"an-001", "pageId":"pg-iqc-report", "nodeId":"n-table",
  "anchor": {"x":0.42,"y":0.18}, "body":"...", "severity":"major",
  "affects":["componentTree","capability"], "status":"open" }
```

- `anchor` 是**相对锚定节点**的 0~1 归一化坐标，不是页面绝对像素。所以换页、改栏宽、换窗口大小、重开浏览器，pin 都不跑位。
- `nodeId` 必须在本页组件树内（L2-38 校验）。锚到不存在的节点，pin 会飘到页面左上角。
- 交互流程：点「标注」→ 点页面元素 → 写一句 → 保存。导出为「修改指令」，每条含定位 + 动作 + 现状，可直接喂给下一轮。

## 7 持久化

`localStorage` 按 `iiot:{产品}:{版本}` 分键存三样：

| 键 | 内容 | 重置影响 |
|---|---|---|
| `pageId` / `pageState` / `entityStatus` | 上次看到哪 | 无 |
| `annotations` | 标注（与 `proto.json` 里的初始标注合并） | 会丢人工标注 |
| `prdEdits` | PRD 正文的在线编辑 | 会丢编辑 |

「重置为 AI 版本」= 清这三个键，回到 `proto.json` 的原始状态。版本号进 key 是有意的：换版本时旧标注不会串到新原型上（`nodeId` 可能已经变了）。

## 8 导出

| 导出 | 机制 | 稳定性 |
|---|---|---|
| PRD → Markdown | 遍历 `prd.sections` 拼 md | 稳 |
| 当前页 → 单页 HTML | 抽出该页 DOM + 内联样式，生成独立文件 | 稳，前端可直接用 |
| 标注 → 修改指令 | 拼成结构化文本 | 稳 |
| 当前页 → PNG | SVG `foreignObject` 包 DOM → canvas | **需浏览器实测**，跨域字体和图片会失败 |
| 打印 / 存 PDF | `@media print` 隐藏壳，只留原型 | 稳 |

字段字典章节由 `build_prd` 生成，容器面板与 `#export=md` 共用同一套块 id（`field-{pageId}-{siteId}-{key}`）。手改 PRD 交付前先跑 `check_parity --prd`，C-22 会指出少/多哪一块。

PNG 那条要留意：`foreignObject` 方案在 Chrome 上通常可行，但页面里有外部字体或图片时会被 tainted canvas 拦住。第一版交互时验证一次，不稳就把 PNG 降级为"打印存 PDF"。

分享某个具体状态给评审，比口头描述省一半时间：

## 10 加一个组件

四步，顺序不能反：

1. **登记** `schemas/catalog.json`：`category`（pc-shell / pc-input / pc-data / pda / common）、`states`、`props` 契约。不登记 → 运行时降级成虚线框 + L2-14 红。
2. **实现** `components.js`：options API + `h()`，`props: { p, n, ctx }`，只用 `p` 里的数据。
3. **加样式** `styles.css`：只能用设计令牌，不写死颜色值。
4. **验证**：改 `example-01` 用上新组件 → `check_contract.py` → `build.py` → 截图看四态。

第 4 步不能省。组件在 `default` 态好看、`empty` 态塌掉，是最常见的问题。

## 11 交互引擎：能点是契约的一部分

老版容器的毛病很典型：`interactions` 在 schema 里有、校验器也查、引擎从来不读。于是"点击行进入详情"只存在于 JSON 里，页面上点下去什么都不发生，评审时没人敢信这台原型。

现在引擎把四件事接上了：

### 11.1 点击由 interactions 驱动

页面根节点上挂一个事件监听：点到的元素往上找到 `[data-node-id]`，拿它的 id 去本页 `interactions` 里找 `on` 相同的条目，执行 `do`。

引擎实现的动作集合是封闭的（L2-59）：`navigate` / `openModal` / `openDrawer` / `setState` / `submit` / `toast` / `reset`。契约里写了别的值，校验器直接红，而不是运行到那一刻才发现没反应。

表格行点击是特例，用 `on: "__row_click"` 表示，由 `RD.selectRow` 处理——它既要记选中行，也要执行交互（通常是 `navigate` 到详情）。

### 11.2 承载层按 `capabilities[].ui` 渲染

`RD.action` 先看命令有没有 `ui`：

| `ui.kind` | 引擎行为 |
|---|---|
| `inline` | 直接执行命令：推进状态、给 toast |
| `dialog` | 打开居中弹框，宽度取 `ui.width`（默认 560） |
| `drawer` | 从右侧滑入，宽度默认 520，贴顶贴底 |
| `page` | `RD.goto(ui.pageId)`，跳独立页面 |

弹层里有三样东西必须有：标题（`ui.title`，缺省用命令名）、字段（`ui.fields` 渲染成表单）、主按钮（`ui.submitLabel`）。没有 `fields` 也没有 `successText` 的命令，弹出来是空壳（L2-63）。

**没有按钮的动作不是命令。** `capabilities` 的定义是"用户能发起的动作"，每条都必然有入口（按钮、扫描枪、菜单）。定时任务、回调、超时自动关闭这类"没人点它也会发生"的动作，写状态机的系统迁移：

```json
"transitions": [
  {"from": "approving", "to": "closed", "trigger": "system-timeout", "system": true}
]
```

以前 schema 里有个 `placement: "none"` 想给这类动作当第二个家，已经删掉了（与 `isFilterView`、`meta.skin` 同一个病：给同一件事开第二个字段）。容器也从来没支持过它——`ui.kind` 只有 inline/dialog/drawer/page 四个值，`ui.entry` 必填，写 `none` 连一条合法契约都组不出来。现在写 `none` 会被 `L2-85` 判非法值，报错文案里直接指路 `transitions[].system`。

同一处还有两条边界：`to` 不许落在 `from` 里（`L2-94`，自环等于"声称改状态、改完还是它"，状态图上画出一个指向自己的箭头，读图的人会以为这一步能重来）；不改状态的动作用 `to=null`，不要拿自环凑。`from=[]` + `to` 等于状态机 `initial` 是**建单命令**的写法，`L2-77` 为它开了豁免——它本来就该一直亮着。

**关闭通道四条都要通**：右上角 `×`、底部「取消」、「Esc」、点遮罩。少一条，评审时就会有人卡在弹层里刷新页面。Esc 监听挂在 `window` 上，所以要判断当前有没有弹层再决定是否拦截。

### 11.3 提交 = 校验 + 状态推进

`submitLayer` 做三件事：

1. 按 `fields[].required` 校验，缺的字段标红并 toast「还有必填项没填：X、Y」，**弹层不关**；
2. 通过后用 `cap.to` 查状态机拿中文标签，推进状态：行级命令（措施单、逐条验证）改 `L.row.status`，单据级命令改 `store.entityStatus`；
3. 关弹层 + toast 结果（`ui.successText` + 新状态）。

### 11.4 数据必须响应式

`var DATA = window.__PROTO__` 是普通对象时，行级命令改了某一行的 `status`，Vue 追不到，表现是"提示提交成功，列表还是旧状态"——比报错更糟，因为用户以为生效了。所以容器初始化时 `DATA = Vue.reactive(window.__PROTO__)`。

配套的：行状态变了，该行的按钮可用性要跟着重算（`can()` 每次渲染时用当前状态求值，不在渲染时算一次就缓存）。

### 11.5 目录必须点得动

`AppShell` 的导航项以前是纯 `<div>`，没有点击处理——看着是菜单，点着没反应。现在：

- 导航项优先用显式 `page` 字段绑定；没写的按 `label` 去匹配页面标题；
- 匹配上了 → `RD.goto(pageId)`，并按当前页高亮（`is-on` 由 `store.pageId` 实时算，不信数据里的 `on`）；
- 匹配不上 → 标 `is-void` + 点击给一句原因（「不在本原型范围」），不做假菜单。

页头标题必须等于页面名（L2-62）。拿某条单据号当页头标题，换一条数据进来就张冠李戴。

### 11.6 实测：别再说"应该能点"

```bash
python3 scripts/check_interact.py \
  --proto examples/example-02-accident.proto.json \
  --html examples/dist-accident.html
```

它从契约里推出用例：每条 dialog/drawer 命令点开一次、看承载形式对不对、按 Esc 看关不关得上；每个目录项点一次、看页面有没有换；每个列表页点一次、看进不进详情。无头 Chrome 跑，输出逐条 OK/FAIL。

这一层专门抓"契约齐全但引擎不认"：把引擎里 `openLayer` 那行注释掉重跑，9 条命令立刻红。

#### 承载用例的三级判定（R-10）

"这条命令的入口点得开吗"这一个问题，背后混着两件事：承载层没实现、mock 数据里没有能触发的行。硬让它报红，等于让它替数据层背锅。所以分成三级：

| 情形 | 级别 |
|---|---|
| 默认「不限角色」下 `[data-cap]` 根本不在 DOM | **ERROR**：契约说有入口，页面上没有，无歧义 |
| 在 DOM 但全 `is-off`，且状态能到位（表级拨顶栏、行级看该列 `stateKey` 的实际取值）仍点不开 | **ERROR**：引擎的事 |
| 在 DOM 但全 `is-off`，压根没有一行落在 `from` 上 | **WARN**：`分不清是没实现还是没数据`，交给 C-21 |
| 点开了但没有承载层 / 承载层是空壳（正文无子节点） | **ERROR** |

行级与表级拨状态不是一回事：行级按钮吃的是这一行的 `stateKey`，拿主单状态去拨会造出"我明明拨到 `from` 了它还是灰的"这种假红。

#### C-21：让那个 WARN 有人接

只降级不补判据，就会出现"一个弹层永远打不开，报告里只占一行 WARN，半年后没人记得它是什么意思"。所以配一条数据层判据：

**C-21**：`to != null` 的命令，其 `from` 至少有一个状态出现在**它所在表格的** `data[].{stateKey}` 里。表级/表单级命令没有 `data`，改为校验 `from` 的键在状态机里存在。

`cap.from` 存的是状态 key、`data[]` 存的是 label，比对前要经状态机做 `key → label` 映射，两边都认。

#### 一条原则：同一根因只在一个层级报红

不写这条，报告就会变成"谁先跑到谁报红"——同一个根因出现两次、一次 WARN 一次 FAIL，读的人以为有两个问题，然后去修两个地方。

- 数据没铺到 → **C-21 报 ERROR**（修法在数据层）
- 数据到位、入口仍点不开 → **R-10 报 ERROR**（修法在引擎层）
- R-10 只把"它分不清的那一类"降 WARN，**不替 C-21 下判断**

实测：把两条命令的 `from` 改成一个数据里没有的状态，C-21 出 2 条 ERROR，R-10 与 R-08 各降 WARN —— 一个根因，一处红。

**预算跟着用例数自动算**（`max(60s, 用例数 × 6s)`，上限 300s），不需要记忆"用例多了要调 `--budget`"。这条坑的起因是角色覆盖从 2 条涨到 16 条之后总时长翻倍，默认 60s 装不下，跑出来一片假失败——让人去记一条公式，等于把引擎的问题转嫁成使用者的记忆负担。上限 300s 的意义是：撞到上限说明页面里有东西一直在排任务，那不是"用例太多"，加预算解决不了，得去查那个死循环。

### 11.7 截图只在验收时截，验完就删

原型核验会反复截同一批页面，很容易留下几十张中间态。约定：

- 每轮截图**覆盖同名文件**，不叠 `r_` / `s_` / `t_` 这种轮次前缀；
- 只保留终版整页图 + 异常态各一张，其余验完即删（进废纸篓，不是硬删）；
- 局部裁切图（看列宽、看间距）用完就删，它只是过程证据。

**清空废纸篓时会被 TCC 静默挡住**：macOS 对 `~/.Trash` 有隐私保护，没有"完全磁盘访问"授权的终端进程执行 `rm -rf ~/.Trash/xxx` 会**返回 0 但一个文件都没删**（`mv` 进废纸篓却是允许的，所以看不出问题）。要真删，先移出这一步：`mv ~/.Trash/<目标> /tmp/<目标> && rm -rf /tmp/<目标>`，删完用 `find /tmp/<目标> -type f | wc -l` 确认是 0。别看到 `rm` 没报错就以为清完了。

### 11.8 三个"空块"：契约写了、引擎没读

做事故报告正式交付时连撞三次同一类问题——**JSON 里字段一个不少，页面上那一块是空的**。
三个都不是写错数据，是引擎读的键和契约写的键不是同一个：

| 现象 | 根因 | 修法 |
|---|---|---|
| 详情页顶部「单据状态」只有标题，后面一条空线 | `StatusBar` 只读 `props.steps`，契约给的是 `props.stateMachine` | 组件里补回落：无 `steps` 时按 `stateMachine` 去 `stateMachines` 取 `states` |
| 新建页整张表单显示「暂无字段」 | `FormGrid` 只读 `props.items`，契约写的是 `props.fields`（与命令弹层的 `ui.fields` 同名同义） | `var items = p.items \|\| p.fields \|\| []` |
| 状态条右侧的单据编号 / 发生时间 / 停留天数全不见 | `StatusBar` 只渲染 `props.note`，不认 `props.meta` | 把 `meta` 拼成一段次要文字渲染在右侧 |

三条都补了判据（`L2-64` 状态条必须有 `steps` 或存在的 `stateMachine`；`L2-66` 表单必须有 `items`/`fields`），
因为这类问题**靠看 JSON 永远发现不了**——契约校验全绿，页面却是残的。

推论：新增组件时，props 的键名要么和已有约定一致（表单字段一律 `fields`），要么在组件里同时兼容两种写法。
**"我写了一种、引擎认另一种"是原型返工里最贵的一种错**，它不会报错，只会安静地渲染成空白。

### 11.9 弹层的上沿：让开外壳，只压内容

`.layer-mask` 原来写的是 `inset: 0`，等于连顶部工具条一起罩住。后果不是"少点一个按钮"，而是**弹框一开，目录 / 标注 / 审核 / PRD / 导出 整排全哑**——评审时最常见的动作恰恰是"开着弹框顺手点标注圈一下"。

外壳和内容的分界要写进令牌，不能靠眼估：

| 层 | 高度 | 弹层怎么对待 |
|---|---|---|
| `.shell-top` 顶部工具条 | `--h-topbar`（44px） | 不许盖，遮罩从它下沿开始 |
| `.app-header` 页头 | `--h-header`（52px） | 属于内容区，被压暗是正常的 |

三处改动：`.layer-mask` 用 `top: var(--h-topbar)` 取代 `inset: 0`；`.layer` 的 `margin-top` 从 64 改 20、`max-height` 扣掉顶栏高；`.layer-drawer` 的 `top` 从 0 改 `var(--h-topbar)`。

`check_interact.py` 里加了 `topbarUsable()`，每条弹层用例打开后做两件事：量遮罩上沿是否低于顶栏下沿、在顶栏按钮中心做 `elementFromPoint` 命中测试（拿到 `.layer-mask` 就是被盖了）。造红验证：把 `inset: 0` 改回去，12 条里 9 条弹层用例立刻失败并报「遮罩盖住了顶部工具条」。

注意 `elementFromPoint.apply(null, [...])` 在页面上下文里会抛 `Illegal invocation`，直接调用即可。

### 11.10 目录是树，不是一排平行项

一层平铺在 10 个菜单以内能用。到 30 个，用户就靠记忆找位置了——找不到就以为没有这个功能。

结构（`navItem` 可递归）：

```json
{ "title": "质量管理", "items": [
  { "key": "accident", "label": "事故报告", "children": [
      { "key": "acc-ledger", "label": "事故台账", "page": "pg-acc-ledger" },
      { "key": "acc-mine",   "label": "我的措施任务", "page": "pg-acc-mine" }
  ]},
  { "key": "capa", "label": "纠正预防措施", "count": 9 }
]}
```

三条展开规则，缺一条都会让人多点两下：

1. **当前页所在分支强制展开**，与用户上一轮的手动开合无关——否则换页后高亮项藏在折叠里。
2. **一级默认展开，二级起默认收起**。全展开等于没折叠；全收起等于多一步。
3. **折叠状态按 `key` 记进 localStorage**（`store.navOpen`）。按 `label` 记会在改名后失效，按索引记会在插入菜单后错位。

搜索框是真输入框，不是装饰：输入即过滤，命中项带完整路径（`质量管理 / 事故报告`），点了直接跳。命中后清空搜索词，否则用户下次打开还停在过滤态。

层级上限 3 层（`L2-67`）。超过三层就不是导航，是文件夹浏览器——该拆模块了。同层 `key` 不得重复（`L2-68`），否则两个节点会一起开合。有子项的分组至少要有一个能落到页面（`L2-69`），全灰的分组会让用户以为整个模块坏了。

### 11.11 标注要活得比原型久

原型是活的：页面合并、字段改名、弹层重做。如果标注跟着 `nodeId` 一起消失，**每一轮评审都从零开始**，前面标过的意见没人记得。

三处配套改动：

| 问题 | 改法 |
|---|---|
| 升版后标注全丢 | 存储键 `iiot:{产品}:{模块前缀}`，**去掉版本号**；加载时与 `DATA.annotations` 按 id 合并（本地优先，除非契约里已带 `resolution`） |
| 弹框/抽屉里标不了 | 弹层字段带 `data-node-id="layer:<capId>:<key>"`；标注层从画布内 (`position:absolute`) 提到视口 (`position:fixed`)，`z-index` 高于遮罩 |
| 落点元素没了怎么办 | 保存时存 `target` 快照（页面名 + 元素名 + 弹层归属）；找不到元素就不画 pin，但卡片保留并标「落点已失效」 |
| 标了"已完成"看不出改了什么 | `resolution` 必填（`L2-70`），卡片上常驻绿色解决方法块；导出的修改指令里已完成部分一并附上 |

坐标要跟着载体一起改：pin 用 `getBoundingClientRect()` 的视口坐标，不要再减画布原点。减了就会出现"弹层一开，pin 偏移 96px"。

造红方式：把 `.layer-mask` 的 `top` 去掉、或把 `KEY` 改回带版本号，前者 9 条弹层用例红，后者重载后 `annotations` 直接归零。

### 11.12 页面目录也是树

左侧菜单解决"用户怎么干活"，顶栏「目录」打开的**页面目录**解决"这份原型一共几页"。两件事，两棵树。

平铺的代价在页数上去之后才显形：一个模块十几页，找页就是扫名字。所以 `modules[].pageGroups` 让页面按功能聚合：

```json
"pageGroups": [
  {"key": "acc", "title": "事故报告单据", "children": [
    {"key": "acc-ledger", "title": "事故报告台账", "page": "pg-acc-ledger"},
    {"key": "acc-new",    "title": "新建事故报告", "page": "pg-acc-new"}
  ]}
]
```

三条兜底，保证**任何契约都不会退化成平铺**：

| 优先级 | 依据 | 什么时候用 |
|---|---|---|
| ① | `modules[].pageGroups` | 策划时按功能分好的组，最准 |
| ② | `pages[].parentId` | 契约里本来就有的层级，只是以前没人读 |
| ③ | 页面 `layout` | 都没有时按用途分组：列表页 / 详情页 / 表单页 |

树的坑和平铺不一样，判据盯的也就不同：

- **漏页**：一页没进目录，在平铺里只是少一行，在树里就是"这页不存在"。`L2-74` 要求模块内每一页都出现且只出现一次。
- **重复挂载**：同一页挂在两个组下，用户不知道从哪进，改完也容易只改一处。`L2-74`。
- **空壳组**：组展开后一页都没有，点开只能折叠。`L2-74`。
- **层级与 key**：超过 3 层、同层 key 重复，和菜单树同一套 `L2-73`。

交互实测同时守两件事：分组**真的会折叠**（行数要变）、叶子**真的会跳页**，而且跳完**面板要收起来**——它是覆盖层，不收就把目标页面又挡住了。

> 踩过的坑：竖线原本写 `border-left: 1px dashed var(--line-3)`，而这个令牌根本不存在。CSS 变量未定义不会报错，整条声明失效，于是线一直没画出来，看起来"设计上就没有竖线"。写令牌前先在 `:root` 里确认它有定义。

### 11.13 角色开关：让四眼校验在容器里点得出来

契约里写 `actor: ['u-qa']`，"执行人看不到审核按钮"这句话在图纸上成立；但容器不切角色，这条规则在原型里根本演示不出来——评审时只能靠讲解，讲解是最容易漏的一环。

顶栏因此多一个「当前角色」下拉（`data-role-switch`），切的是 `store.currentUser`，写 localStorage，和页面、单据状态一个桶。

**默认值是「全部角色（不限）」，不是第一个角色。** 原型是给一群人评审的，一进来就按某个岗位过滤，别的角色会以为"这个按钮没做"。只有明确切到某个岗位时，才按 `cap.actor` 过滤。

切到没权限的角色之后，被挡住的按钮**不画**，原来是按钮的位置留一句话：

| 位置 | 文案 |
|---|---|
| 工具栏 | 当前角色在本页没有可用操作 |
| 表格操作列 | 无可用操作 |

空白比置灰更糟：空白既像"还没做完"，也像"渲染挂了"，人和脚本都读不出结论。

R 层因此多四条，前两条必须成对跑：

| 用例 | 断言 |
|---|---|
| `R-06` | 切到确实没权限的角色，这批推进命令在 DOM 里**一条都找不到**；操作格与工具栏**都不能是空白**；整列动作都被滤光时格子里要出现「无可用操作」 |
| `R-07` | 切回有权限的角色，这批命令回来，**而且点得开**（承载层弹出、Esc 关得上） |
| `R-08` | **一进页面那一刻**顶栏选中的是「全部角色（不限）」，且本页推进命令全部渲染、全部是启用态 |
| `R-09` | 绕过界面直接调 `RD.action`：角色不对要拒、行状态不对也要拒，两次都断言**载体状态没变** |

只测 R-06 不看 R-07 是不够的：把按钮整个删掉，R-06 也绿。

R-08 守的是"默认值静默漂移"。默认值只要从「不限」改成第一个角色，页面一进来就少一批按钮，而 R-06/R-07 照样全绿——它们自己会切角色，切完看到的都是对的。所以 R-08 读的是启动时的值（探针在跑任何用例之前先记下来），不是跑完一圈之后的值：那时开关早被前面的用例拨回「不限」了。

同一条用例里还要对拍一次 `RD.can`：`can(id, state)`（第三参缺省）与 `can(id, state, '')`（顶栏「不限」传的空串）必须给出同一个结论，再拿一个真无权角色证明"拒"这件事本身没坏。少了第三条，两边都放行也能过——测的就不是合流，是真空。

`R-09` 不是"安全"（原型没有后端，拦不住谁），是**保真**：状态机的可达集被脚本扩大以后，导出给业务方评审的 mermaid 状态图就不再描述这台原型真实能走的路。所以它断言的是"载体状态没变"，不是"弹了个 toast"——toast 可以弹了却不 return。用例里带一条正对照（角色对、状态对时必须真推进），否则 `action()` 整个空转也能让两条"没变"同时成立。

**创建命令只测角色那一半。** `from=[]` 且 `to` 等于状态机 `initial` 的命令（填完表单落库），动作前后 `entityStatus` 恒等于 `initial`：断言"状态变了"恒假，断言"被设成 to"恒真，两个都是空断言。所以这类命令 R-09 只验"角色不对要拒、角色对要真执行"（执行痕迹用 toast 文案判），状态约束归 `L2-77` 的建单豁免，数据覆盖归 `C-21`。**判据不该为了凑覆盖率去断言恒真恒假的东西。**

同理，`to` 落在 `from` 里的自环命令由 `L2-94` 在契约层直接报错——它推进完状态不变，R-09 的正对照根本无从判断，只能跳过。**一条会给自己制造永久盲区的命令，应该在建契约时就被拦住，而不是让测试脚本绕着它走。**

> 踩过的坑一：`rendered_caps()` 一开始只认 `props.actions[].capability` 和 `columns[].actions[].capability`，漏了单按钮节点的 `props.capability`（PDA 的 BigAction 就是这么挂的）。结果 PDA 页上那条命令对判据完全隐形，`L2-90`/`L2-91` 都看不见它。三种写法必须一起扫。
>
> 踩过的坑二：R 层原来按文字找按钮。台账行内有「审核」、顶栏也有「审核」，DOM 顺序上顶栏在前，探针一直在点顶栏那个，报出来的失败是"点了没弹层"。改成按 `data-cap` 找之后才暴露出真正的问题：那条命令的 `from` 是 `reported`，而页面默认落在 `sampled`，按钮本来就是灰的。**找错元素比找不到元素更危险**——它会给出一个看起来很具体的错误结论。

### 11.14 校验前先重建：默认 `--html` 是"上一次构建"的产物

`check_parity.py` / `check_interact.py` 的默认 `--html` 指向 `assets/container/dist/index.html`，
那是**上一次 `build.py` 写进去的页面**，不一定是你当前手上这份契约的产物。

改了契约或组件后直接跑，会一次冒出十几条 `C-03 / C-05 / C-07 / C-09`：页头写着别的页面名、
路由不在 MD 里、契约 10 列容器 11 列——看着像判据坏了，其实是**拿 A 产品的 DOM 比 B 产品的契约**。
这种红绿都没有意义，而且最容易得出"判据太严"的错误结论。

规则：

1. 改完契约/容器，先用**当前契约**重建产物：`python3 assets/container/src/build.py --proto <abs proto> --out <abs html>`；
2. `--html` 显式指向刚建的那份；交付版、用户工程的产物路径不同，不能靠默认值；
3. 只跑 `check_contract` 不需要产物，改 schema/判据时它先绿，再谈 C/R 层。

## 12 已知限制

| 限制 | 影响 | 缓解 |
|---|---|---|
| 单文件体积随页面数线性增长 | 36 页以上超过 1.5MB，首次打开变慢 | 超过 36 页时按模块拆成多个 HTML，或只内联当前模块 |
| 无路由，靠 `store.pageId` | 浏览器前进/后退不可用 | 用 `#page=` 直达；交互跳转已可用，浏览器历史栈不记 |
| 表单只校验必填，不校验业务规则 | 前端必填能演示，规则校验（如限值范围）仍要真实后端 | 规则写在 `guards` 里，真实前端按它实现 |
| 角色是手动切换的模拟值 | 不是真实登录态，刷新靠 localStorage 记住 | 契约里 `actor` 已定义，真实系统按它做鉴权；容器这一层只负责把规则演出来 |
| 标注只存在本机 localStorage | 换电脑/换浏览器看不到上一轮的意见 | 用「导出修改指令」交接；正式留痕写回契约 `annotations[]` |
| PNG 导出依赖浏览器 | 见 §8 | 降级为打印存 PDF |
