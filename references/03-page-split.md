# 页面拆分与四类结构统一

> 这个需求的页面会做到 60+ 张（QMS 一个模块就 20 张）。靠命名约定一定乱，靠"感觉该拆了"一定反复推翻。这份文档给三刀切分规则、每条规则的可判定标准，以及原型 / 交互 / 状态 / PRD 四类结构如何统一到同一份 JSON。

## 1 三刀切分：模块 → 页面 → 子页面

```
业务域（模块）        来料检验 / 过程检验 / 不合格品 / 供应商管理
  └ 页面（一个任务）   来料检验报告  ·  取样任务(PDA)
      └ 子页面/抽屉    报告详情 / 取样历史 / 标准限值
```

三层的判据完全不同，混着用是大部分页面清单失控的原因：

| 层 | 判据 | 一句话检验法 |
|---|---|---|
| 模块 | **按业务域切，不按角色切、不按菜单切** | "这块业务归谁负责？"——归属不同部门就是不同模块 |
| 页面 | **一个页面只承担一个 `contract.task`** | 用一句话说完这页干什么，**句子里不能有"和"** |
| 子页面 | **一个子任务，且不改变主任务的状态** | "看完这个我能回到主任务继续吗？"能就是子页面 |

模块按角色切是最常见的错误：「取样员工作台」「工程师工作台」听起来合理，但同一个"来料检验"业务被劈成两半，状态机要写两遍，改一次改两处。**角色是 `capabilities[].actor`，不是模块边界。**

### 切完顺手把页面目录分了组

页面定下来之后，`modules[].pageGroups` 要和页面一起写，别留到最后补——等到二十几页再分，就只能按名字猜哪几页是一件事了。

分组的原则只有一条：**同组的三页，是同一个岗位在同一个任务里会连续用到的**。

```json
"pageGroups": [
  {"key": "acc", "title": "事故报告单据", "children": [
    {"key": "acc-ledger", "title": "事故报告台账", "page": "pg-acc-ledger"},
    {"key": "acc-new", "title": "新建事故报告", "page": "pg-acc-new"},
    {"key": "acc-detail", "title": "事故报告详情", "page": "pg-acc-detail"}
  ]},
  {"key": "measure", "title": "措施", "children": [
    {"key": "measure-mine", "title": "我的措施", "page": "pg-measure-list"}
  ]}
]
```

- 别按"列表/详情/表单"分——那是渲染方式，不是业务。引擎推不出来时才这么兜底。
- 分组不带 `page` 就别让它是空壳：展开后一页都没有的组，等于给用户挖了个坑（`L2-74`）。
- 一页只归一组。既想看全量又想看自己的，那是两页（见 §4），不是一页挂两处。

## 2 页面的五条硬判据

`pages[]` 里每一条都要过这五关，过不了的说明该拆或该合：

### 判据 1：一句话不含"和"

```
✅ 质量工程师审核来料检验报告
❌ 质量工程师审核报告和管理检验标准
```

第二条要拆成两个页面，因为"管理标准"是另一个 actor（技术部）的另一个任务。

### 判据 2：一条命令只有一个主页面

`contract.owns` 里同一命令被两页认领 → L2-21 直接红。这条判据的价值在于：**它逼你想清楚"这个动作到底发生在哪"**。

典型冲突：列表页有"审核"行内按钮，详情页也有"审核"按钮。处理方式二选一：
- 详情页 owns，列表页的行内审核只是**跳转到详情并高亮**（不是直接执行）；
- 列表页 owns（批量场景），详情页的审核按钮**不出现**。

不允许两边都能直接执行——那样状态机触发点有两个，四眼校验、幂等、日志全要写两遍。

### 判据 3：两个"主操作"就要拆

一屏里出现两个同等权重的主动作（提交取样 + 提交复检），说明这是两个场景被塞进一页。PDA 上尤其致命：一屏只能有一个拇指区主操作（L2-49 强制 `BigAction`）。

### 判据 4：节点数 ≤ 80

这是切片预算（P-08），也是页面复杂度的上限。超过 80 个节点，实际渲染出来一屏放不下，用户要滚 3 屏才能看完——那不是"信息密度高"，是没做信息分层。

### 判据 5：四态能各自说清

`states[]` 里 default / loading / empty / error 四态必须都能描述出"这一态长什么样"。说不出来，说明这页的数据来源还没想清楚。

## 3 推进动作：一个动作 = 一个状态 = 一条命令 = 一个权限点

详情页最容易做坏。把「过程排查」「原因分析」「下发措施」做成详情页里的三个可编辑区块，看起来信息齐全，实际是三种角色、三个时点、三套校验塞进一屏：进来的人不知道自己该干什么，也不知道自己填完算哪一步。

**正确做法是把每个推进动作立成单据状态**，谁该做什么由状态决定，不由"他现在打开了哪个页面"决定：

| 动作 | 单据状态 | 命令 | 谁能做 |
|---|---|---|---|
| 到场排查、写现场记录 | 待排查 | `cap-patrol` | 安环员 |
| 分析根本原因 | 待分析 | `cap-analyze` | 安环主管 |
| 下发整改措施 | 待下发 | `cap-issue-measure` | 安环主管 |
| 措施执行 | 措施执行中 | `cap-start-measure` / `cap-finish-measure` | 责任人 |
| 效果验证 | 待验证 | `cap-verify-pass` / `cap-verify-fail` | 安环主管 |
| 审批关闭 | 待审批 | `cap-approve` / `cap-reject` | 质量经理 |

这样切之后，四个问题一起消失：状态清晰（看单据状态就知道卡在哪）、权限自然（命令带 `actor`）、四眼可查（谁在哪一步签的字有轨迹）、页面稳定（详情页不再随流程改版）。

**详情页只读**（L2-54）。详情页的职责是把"已经发生过什么"讲清楚：基本信息、各步结论、措施清单、处理轨迹。它不放可编辑表单——一旦放了，同一个字段就会有两个入口（详情页和推进弹层），改一处漏一处。

### 状态不是页面

这条必须写死，因为它是最容易做歪的一处：**流程阶段多 ≠ 页面多**。

一张单据 = **一个列表页 + 一排工具栏按钮 + 行内动作 + 弹框/抽屉**。状态是行上的一个字段，是按钮亮不亮、点了开哪个层的条件；它**不是**一个页面。单据有 8 个阶段，页面数还是 1 个。

判断"这里该不该多一个页面"只用一句话：**这张表里的人，是不是要看到同一个单子的另一批数据？** 是（比如"这张单的历史操作日志"），才值得单独一页；只是"这张单走到下一步了"，那是状态变了，不是页面变了。

真实系统里长什么样：退货产品处理单的「处置方案」「关闭」全部在台账列表的工具栏上，工序从「待入库检验」到「已完成」走的都是同一张表。做原型时把它拆成「台账」「我的待办」「处置与闭环」三页，用户要在三页之间找同一张单。

所以：

- 推进动作一律做成列表页上的命令，靠单据状态决定亮灭（L2-80 / L2-81）；
- 执行视角（"我的待办"）是这张表的**过滤视图**，不是第二张表，也不是第二套动作（L2-82）；
- 承载载体只有四种：工具栏按钮、行内操作列、表单内提交、弹框/抽屉，全部在列表页上（L2-85）。

### 承载形式按录入复杂度选

同一个动作用弹框还是抽屉，不由审美决定，由"填的时候需不需要看上下文"决定：

| 承载 | 用在哪 | 判据 |
|---|---|---|
| `inline` | 无需录入的确认、导出、提交 | 点完就结束，不填东西 |
| `dialog` | ≤ 6 个字段，且填的时候不用回头看原单据 | 弹框遮住的区域里没有你需要参考的信息 |
| `drawer` | 字段多、要参考列表/上下文逐条填 | 填的时候必须能看见左边那一行数据 |
| `page` | 需要发链接、字段组 ≥ 4 组、有独立权限 | 见下方三条 |

`page` 的三条判据（命中任一即用页面，不用抽屉）：需要被单独分享（`#page=xxx` 发同事）；字段组分 ≥ 4 组（要锚点导航）；有独立的操作权限（这一页里有别人不能点的按钮）。

来料检验报告用页面，因为三条全中：客审要发链接、28 个字段分 4 组、审核权限只给 `u-qa`。事故报告的「过程排查」用抽屉，因为排查人要一边看事故经过一边写结论。

**每条非 inline 命令都必须在契约里声明 `ui`**（L2-55）：

```json
"ui": {
  "kind": "drawer",
  "entry": "n-table__act_patrol",
  "title": "过程排查",
  "width": 560,
  "submitLabel": "提交排查结论",
  "successText": "排查结论已提交",
  "fields": [
    { "key": "arriveAt", "label": "到场时间", "type": "date", "required": true },
    { "key": "finding", "label": "现场情况", "type": "textarea", "required": true,
      "hint": "写清看到什么：设备状态、参数记录、当事人陈述、现场照片编号" },
    { "key": "conclusion", "label": "排查结论", "type": "radio", "required": true,
      "options": ["属安全防护缺失", "属操作违规", "属设备失效", "未发现直接原因"] }
  ]
}
```

不写 `ui` 的后果不是"少个字段"，是**这个动作最后一定被塞进详情页**——因为实现的人没有别的地方可放。

## 4 管理视角与执行视角：两个筛选，不是两套动作

单据的生命周期长到一屏看不完两种人时，一个列表装不下——但**装不下的只是筛选条件，不是动作**：

- **管理视角**（台账）：看全量。筛选器按部门/等级/时间。
- **执行视角**（我的待办）：同一张表 + 同一个筛选维度（我的）。它不定义任何新动作，也不减少任何动作。

两个视角的差别只有两处：默认筛选条件（全部 / 我的）、默认排序（按剩余时限）。**按钮是同一批**——同样是工具栏 + 行内那一排，靠单据状态决定谁亮谁灰。

事故报告因此是 `pg-acc-ledger`（主列表，`listRole=primary`）+ `pg-acc-mine`（过滤视图，`listRole=filter`）。**`contract.owns` 只回答一个问题：这条命令归哪一页负责**（全局唯一，L2-21 没有豁免）。它不回答"这页显示什么"——那是组件树的事：一页渲染了哪些按钮，看 `componentTree` 里的 `capability` 引用；画了就必须有人管（L2-90）。所以过滤视图可以照常渲染主列表那批按钮，也可以自己认领一条纯查询命令，都不算"自造"。整条生命周期（所有 `to≠null` 的推进命令）必须由主列表 `owns`（L2-81），过滤视图 `owns` 里不许出现推进命令（L2-82）。**这条通道是双向的，两头都要闭**：`owns` 里的每条命令，组件树里必须有一处画出按钮（L2-91，没有例外——没有按钮的动作不是命令，是状态机的系统迁移）；画出按钮的页面里，至少得有一个页面的 `actor` 与这条命令的 `actor` 相交（L2-92），否则整条流程里没有任何角色点得到它。至于"某页画了别人的角色才该点的推进命令"，只报 WARN（L2-93）——一张列表把别人的按钮画出来当流程提示是合法设计，但要人看一眼。

主列表选谁，两条规则，按顺序：

1. 有一个覆盖多角色的**管理视角页**（actor 集合明显更宽、看全量）→ 它就是主列表；
2. 所有列表页都是**按角色筛的工作台**（每页一个 actor）→ 主列表 = **动作链起点所在页**（创建者 / 第一个动作的 actor 那一页）。

措施单就是第二种：起点是执行人（`待处理 → 执行中`），所以「我的措施」是主列表，「措施验证」是它的过滤视图——哪怕验证页的按钮更多、命中状态更晚。**别按按钮数量认主，也别为了迁就 `ui.entry` 的宿主页去换主列表**：`entry` 是单值，表达不了"同一个按钮在两页都渲染"。

如果只做一个台账，班长要在一屏里找"哪些是我该做的"，靠肉眼扫状态列——这就是"目录和页面对不上"的来源。但反过来说，**拆成两个列表也不等于就有两个动作集**：把推进动作只挂在"我的待办"的行内，台账上就看不见"入库检验"该在哪点，用户第一次看原型就会问「这个动作在哪做」。

两个列表页的 `contract.actor` 必须有差异，否则只是同一张表换个标题（`L2-58`）。**几个状态就要几个页面**不是规则——"≥4 个人工状态必须拆两页"已作废，一张台账走完全流程是正确做法，判据只看"确实有两页时，主次和角色说清没有"。

## 5 四类结构统一：同一份信息只有一种写法

你要求的"统一 PRD 结构、原型结构、标注结构、状态机结构"，落地就是这张表——每类结构只有一个载体，别处都是引用：

| 结构 | 唯一载体 | 不允许出现在别处 | 关键不变量 |
|---|---|---|---|
| 原型 | `pages[].componentTree` | PRD 正文里不许画结构图描述布局 | 节点 `id` 分配后不改（标注靠它锚定） |
| 交互 | `pages[].interactions` | PRD 里不许写"点击跳转到 XX 页面"的自然语言 | `navigate.target` 必须是真实 pageId（L2-19）；`do` 必须是引擎实现过的动作（L2-59） |
| 命令承载 | `capabilities[].ui` | 组件上不许写"点击弹出弹框"的注释 | `kind` 四选一；`entry` 必须能在组件树里找到（L2-55） |
| 目录 | 页面 `AppShell.props.groups[].items[].page` | 不许只在设计稿里画菜单 | 列表页必须在目录里有入口（L2-61）；页头标题 = 页面名（L2-62） |
| 页面状态 | `pages[].states` | 组件上不许写 `loading:true` | 四态必备，列表页加 `zero-result` |
| 业务状态 | `stateMachines[]` | 组件上不许写 `disabled:true` | 人工迁移的 trigger 必须是已存在命令（L2-27） |
| 标注 | `annotations[]` | 不写在 PRD 正文里当批注 | `nodeId` 在本页树内；`anchor` 归一化 0~1 |
| PRD | `prd.sections[]` | 不新建 md 文件单独维护 | 每页必有 `goal`；有交互必有 `flow` |

**"别处都是引用"这条是整套东西能不能维护的分水岭。** 如果 PRD 正文里又写了一遍"表格有 11 列"，那改列的时候就要改两个地方，第三次一定漏。

## 6 PRD 结构：10 种小节，各有固定职责

`prd.sections[].type` 只有这 10 个值，新增类型要改 schema：

| type | 职责 | 什么时候必须有 |
|---|---|---|
| `goal` | 这页解决谁的什么问题，一句话 | **每页必有**（L2-09） |
| `flow` | 流程图（nodes/edges 渲染 SVG） | 有 `interactions` 时建议有（L2-10） |
| `interaction` | 交互说明：触发→响应→反馈 | 有交互时 |
| `availability` | 按钮可用性矩阵（读 capabilities 自动生成） | 页面有 `contract.owns` 时 |
| `rule` | 业务规则与校验 | 有 `guards` 时 |
| `state` | 状态流转说明（读 stateMachine 自动生成） | 页面受状态机驱动时 |
| `acceptance` | 验收要点（引用 `requirements[].acceptance`） | 有 `requirementIds` 时 |
| `data` | 字段清单与来源（读 `fieldRegistry` 自动生成） | 有表单或表格时 |
| `api` | 接口契约草稿 | 对接外部系统时 |
| `note` | 备注、待确认、口径说明 | 随时 |

三种 type 是**自动生成**的：`availability`、`state`、`data`——它们的数据已经在别处了，PRD 里只做渲染。手写这三种等于抄一遍，抄完就不同步。

判定节点的出边必须带 `label`（L2-12）。这条看着琐碎，但流程图里最没用的就是没有条件标注的菱形——看了不知道走哪条。

## 7 标注结构

标注是"改原型"的输入，不是评论区的附属品。四条设计：

```json
{
  "id": "an-001", "pageId": "pg-iqc-report", "nodeId": "n-table",
  "anchor": { "x": 0.42, "y": 0.18 },
  "body": "操作列的「审核」在已归档状态下应整列隐藏，不是置灰",
  "severity": "major", "status": "resolved",
  "resolution": "改成按行状态只渲染允许的那一个，其余不占位",
  "resolvedAt": "2026-11-03T10:20:00Z",
  "target": { "pageTitle": "来料检验报告", "nodeLabel": "操作列", "carrier": "page" },
  "affects": ["componentTree", "capability"]
}
```

1. **锚定 `nodeId` + 归一化坐标**，不锚定像素。原型重生成、栏宽变化、窗口缩放，标注都不跑位。
2. **`affects` 决定改哪儿**。同一句话改组件树和改命令策略是两个动作，标不清楚就会改错地方。
3. **`severity` 用 `blocker/major/minor/question`**，不用高中低。"question"这一类必须有——评审时大量意见其实是疑问（"这里为什么不显示供应商批次？"），混进 major 里会被当成缺陷去改。
4. **标完成必须写 `resolution`**（`L2-70` 会红）。只写"改了"，下一轮没人知道当时改成了什么，等于这条意见没留下信息。

### 落点会消失，标注不能消失

原型是活的：页面会被合并、字段会被删、弹框会被改。标注的 `nodeId` 因此可能在某一天变得不存在。

处理原则是**保留 + 说明**，不是删除：

| 情况 | 怎么展示 |
|---|---|
| 落点元素还在 | 正常画 pin（已完成的画成绿色） |
| 落点元素被删/改名 | 不画 pin，卡片标「落点已失效」，用 `target.nodeLabel` 说明它原来指哪一块 |
| 整个页面被下线 | 归到「全部页面」视图，标「该页面已不在本版原型里」，要不要留由人定 |

`target` 快照就是为这一天存的：页面名 + 元素名 + 弹层归属。少了它，半年后没人看得懂「n-table__act_3 这里要改」到底指哪儿。

### 落在弹层里的标注

`nodeId` 写成 `layer:<capId>:<fieldKey>`（或 `layer:<capId>:__title` / `__submit`）。评审里「这个弹框字段该拆成两个」这类意见，落点只有弹层里才有——钉在整页上说不清。

这类标注只在对应弹层打开时画 pin，其余时间留在卡片里。`target.carrier` 记 `dialog` / `drawer`，卡片上会注明「弹层内」。

## 8 分批交付（内部叫"切片"）

> 给业务方的一律说「**第几批**」。「切片」这个词他们第一反应是数据分析或图片裁切，不知道你在说什么。对内的技术讨论继续叫切片没关系，但写进 A3 汇报就换词。

60 个页面一次生成，结果一定是前 10 页精致、后 50 页模板化。分批的硬上限（P-05~P-08）：

| 维度 | 上限 | 理由 |
|---|---|---|
| 页面数 | 4 | 超过 4 页，单次输出的细节密度必然下降 |
| 命令数 | 6 | 命令多了，按钮矩阵组合爆炸（状态 × 角色 × 命令） |
| 需求数 | 12 | 一条需求平均 3 条验收，12 条就是 36 条验收，再多测不过来 |
| 节点预算 | 80 | 单页复杂度上限 |

切片还要满足三条：

1. **可独立验收**（`acceptance` 必填，P-09）——不能等下一片做完才知道这片对不对；
2. **依赖成环即红**（P-11）——A 依赖 B、B 又依赖 A，说明切法错了，不是画图工具的问题；
3. **一片内自带闭环**——来料检验切片把 PC 报告页和 PDA 取样页放在一起，因为只做一个，另一个的数据就是假的。

## 9 命名约定

命名不是审美问题，是**可校验性问题**。`check_contract.py` 的白名单和端判定全靠前缀：

| 对象 | 规则 | 例 |
|---|---|---|
| 模块 | `m-` + 业务域缩写 | `m-iqc` |
| 页面 | `pg-` + 模块 + 任务 | `pg-iqc-report` / `pg-iqc-sample-pda` |
| 命令 | `cap-` + 动词 | `cap-submit-sample` / `cap-approve` |
| 状态机 | `sm-` + 实体 | `sm-inspection` |
| 需求 | `REQ-` + 三位 | `REQ-002` |
| 标注 | `an-` + 三位 | `an-001` |
| 节点 | `n-` + 语义 | `n-table` / `n-btn-submit` |
| 角色 | `u-` + 岗位 | `u-qa` |

页面的 `-pda` 后缀不是装饰：端判定既看 `target` 字段，也建议看后缀——两者不一致是端错配的高发点。

## 10 自查清单

拆完页面，按顺序问这 13 句，任何一句答不上就回去改：

1. 每个页面的 `task` 能不能一句话说清"这页替谁干什么"？（长一点没关系，一张台账本来就要承载整条流程；说不清"替谁"才是问题）
2. 有没有哪条命令被两页 owns？（**一条命令只能有一个认领页，没有豁免**；过滤视图靠组件树里的 `capability` 引用渲染按钮，不重复认领，L2-21）
3. 有没有哪页有两个同等权重的主动作？
4. 每页的四态都能描述出来吗？
5. **每个推进动作是不是各自一个状态、一条命令、一个权限点？**（不是就退回详情页了）
6. **每条 dialog/drawer 命令声明 `ui.fields` 了吗？**（没声明，实现时只能塞进详情页）
7. **详情页里有没有可编辑表单？**（有就说明动作没状态化）
8. 同一张单据有多个列表页时，是不是**主列表 + 它的过滤视图**（`listRole=primary` / `filter`，恰一个 primary）？主列表是按"管理视角"还是"动作链起点"选的（§4 两条）？两页的 `contract.actor` 有差异吗？**整条生命周期都在主列表 `owns` 里吗？**
9. **每个列表页在目录里点得到吗？页头标题和页面名一致吗？表单页 / 详情页有没有被挂进左侧业务菜单？**
10. **组件树里渲染的每个按钮，都有页面 `owns` 它吗？**（画了没人管，状态和置灰原因就没人负责，L2-90）**反过来，`owns` 里的每条命令，界面上找得到按钮吗**（L2-91）**？画出它的页面里有人点得到它吗**（L2-92）**？**
11. PRD 正文里有没有重复描述组件树的内容？（有就删）
12. 每个判定节点的出边都有 label 吗？切片数量在预算内、依赖不成环吗？
13. **这台原型真点一遍了吗？**（`check_interact.py`，不是"应该能点"）
