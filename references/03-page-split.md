# 页面拆分与四类结构统一

> 这个需求的页面会做到 60+ 张（QMS 一个模块就 20 张）。靠命名约定一定乱，靠"感觉该拆了"一定反复推翻。这份文档给三刀切分规则、每条规则的可判定标准，以及原型 / 交互 / 状态 / PRD 四类结构如何统一到同一份 JSON。

## 1 三刀切分：模块 → 页面 → 子页面

```
业务域（模块）        来料检验 / 过程检验 / 不合格品 / 供应商管理
  └ 页面（一个任务）   来料检验报告  ·  取样任务(PDA)
      └ 子页面/抽屉    报告详情 / 取样历史 / 标准限值
```

三层的判据完全不同，混着用是大部分页面清单失控的原因：

| 层 | 判据 | 一句话检验法 |
|---|---|---|
| 模块 | **按业务域切，不按角色切、不按菜单切** | "这块业务归谁负责？"——归属不同部门就是不同模块 |
| 页面 | **一个页面只承担一个 `contract.task`** | 用一句话说完这页干什么，**句子里不能有"和"** |
| 子页面 | **一个子任务，且不改变主任务的状态** | "看完这个我能回到主任务继续吗？"能就是子页面 |

模块按角色切是最常见的错误：「取样员工作台」「工程师工作台」听起来合理，但同一个"来料检验"业务被劈成两半，状态机要写两遍，改一次改两处。**角色是 `capabilities[].actor`，不是模块边界。**

## 2 页面的五条硬判据

`pages[]` 里每一条都要过这五关，过不了的说明该拆或该合：

### 判据 1：一句话不含"和"

```
✅ 质量工程师审核来料检验报告
❌ 质量工程师审核报告和管理检验标准
```

第二条要拆成两个页面，因为"管理标准"是另一个 actor（技术部）的另一个任务。

### 判据 2：一条命令只有一个主页面

`contract.owns` 里同一命令被两页认领 → L2-21 直接红。这条判据的价值在于：**它逼你想清楚"这个动作到底发生在哪"**。

典型冲突：列表页有"审核"行内按钮，详情页也有"审核"按钮。处理方式二选一：
- 详情页 owns，列表页的行内审核只是**跳转到详情并高亮**（不是直接执行）；
- 列表页 owns（批量场景），详情页的审核按钮**不出现**。

不允许两边都能直接执行——那样状态机触发点有两个，四眼校验、幂等、日志全要写两遍。

### 判据 3：两个"主操作"就要拆

一屏里出现两个同等权重的主动作（提交取样 + 提交复检），说明这是两个场景被塞进一页。PDA 上尤其致命：一屏只能有一个拇指区主操作（L2-49 强制 `BigAction`）。

### 判据 4：节点数 ≤ 80

这是切片预算（P-08），也是页面复杂度的上限。超过 80 个节点，实际渲染出来一屏放不下，用户要滚 3 屏才能看完——那不是"信息密度高"，是没做信息分层。

### 判据 5：四态能各自说清

`states[]` 里 default / loading / empty / error 四态必须都能描述出"这一态长什么样"。说不出来，说明这页的数据来源还没想清楚。

## 3 详情：抽屉还是页面

这是页面清单里最常吵的一个问题。给三条判据，命中任一条用**页面**，否则用**抽屉**：

| 用页面 | 理由 |
|---|---|
| 需要被单独分享（`#page=xxx` 发给同事） | 抽屉没有地址 |
| 字段组 ≥ 4 组（要分组折叠 / 锚点导航） | 抽屉宽度装不下分级信息 |
| 有独立的操作权限（详情页里有别人不能点的按钮） | 权限按页面配比按抽屉配清晰 |

来料检验报告用了页面而不是抽屉，因为三条全中：客审要发链接、28 个字段要分 4 组、审核权限只给 `u-qa`。

## 4 四类结构统一：同一份信息只有一种写法

你要求的"统一 PRD 结构、原型结构、标注结构、状态机结构"，落地就是这张表——每类结构只有一个载体，别处都是引用：

| 结构 | 唯一载体 | 不允许出现在别处 | 关键不变量 |
|---|---|---|---|
| 原型 | `pages[].componentTree` | PRD 正文里不许画结构图描述布局 | 节点 `id` 分配后不改（标注靠它锚定） |
| 交互 | `pages[].interactions` | PRD 里不许写"点击跳转到 XX 页面"的自然语言 | `navigate.target` 必须是真实 pageId（L2-19） |
| 页面状态 | `pages[].states` | 组件上不许写 `loading:true` | 四态必备，列表页加 `zero-result` |
| 业务状态 | `stateMachines[]` | 组件上不许写 `disabled:true` | 人工迁移的 trigger 必须是已存在命令（L2-27） |
| 标注 | `annotations[]` | 不写在 PRD 正文里当批注 | `nodeId` 在本页树内；`anchor` 归一化 0~1 |
| PRD | `prd.sections[]` | 不新建 md 文件单独维护 | 每页必有 `goal`；有交互必有 `flow` |

**"别处都是引用"这条是整套东西能不能维护的分水岭。** 如果 PRD 正文里又写了一遍"表格有 11 列"，那改列的时候就要改两个地方，第三次一定漏。

## 5 PRD 结构：10 种小节，各有固定职责

`prd.sections[].type` 只有这 10 个值，新增类型要改 schema：

| type | 职责 | 什么时候必须有 |
|---|---|---|
| `goal` | 这页解决谁的什么问题，一句话 | **每页必有**（L2-09） |
| `flow` | 流程图（nodes/edges 渲染 SVG） | 有 `interactions` 时建议有（L2-10） |
| `interaction` | 交互说明：触发→响应→反馈 | 有交互时 |
| `availability` | 按钮可用性矩阵（读 capabilities 自动生成） | 页面有 `contract.owns` 时 |
| `rule` | 业务规则与校验 | 有 `guards` 时 |
| `state` | 状态流转说明（读 stateMachine 自动生成） | 页面受状态机驱动时 |
| `acceptance` | 验收要点（引用 `requirements[].acceptance`） | 有 `requirementIds` 时 |
| `data` | 字段清单与来源（读 `fieldRegistry` 自动生成） | 有表单或表格时 |
| `api` | 接口契约草稿 | 对接外部系统时 |
| `note` | 备注、待确认、口径说明 | 随时 |

三种 type 是**自动生成**的：`availability`、`state`、`data`——它们的数据已经在别处了，PRD 里只做渲染。手写这三种等于抄一遍，抄完就不同步。

判定节点的出边必须带 `label`（L2-12）。这条看着琐碎，但流程图里最没用的就是没有条件标注的菱形——看了不知道走哪条。

## 6 标注结构

标注是"改原型"的输入，不是评论区的附属品。三条设计：

```json
{
  "id": "an-001", "pageId": "pg-iqc-report", "nodeId": "n-table",
  "anchor": { "x": 0.42, "y": 0.18 },
  "body": "操作列的「审核」在已归档状态下应整列隐藏，不是置灰",
  "severity": "major", "status": "open",
  "affects": ["componentTree", "capability"]
}
```

1. **锚定 `nodeId` + 归一化坐标**，不锚定像素。原型重生成、栏宽变化、窗口缩放，标注都不跑位。
2. **`affects` 决定改哪儿**。同一句话改组件树和改命令策略是两个动作，标不清楚就会改错地方。
3. **`severity` 用 `blocker/major/minor/question`**，不用高中低。"question"这一类必须有——评审时大量意见其实是疑问（"这里为什么不显示供应商批次？"），混进 major 里会被当成缺陷去改。

标注导出成"修改指令"后直接喂给下一轮：一条指令 = 定位（pageId + nodeId）+ 动作（affects）+ 目标状态。这样迭代不需要人再复述一遍。

## 7 切片：一次只做 4 页

60 个页面一次生成，结果一定是前 10 页精致、后 50 页模板化。切片的硬上限（P-05~P-08）：

| 维度 | 上限 | 理由 |
|---|---|---|
| 页面数 | 4 | 超过 4 页，单次输出的细节密度必然下降 |
| 命令数 | 6 | 命令多了，按钮矩阵组合爆炸（状态 × 角色 × 命令） |
| 需求数 | 12 | 一条需求平均 3 条验收，12 条就是 36 条验收，再多测不过来 |
| 节点预算 | 80 | 单页复杂度上限 |

切片还要满足三条：

1. **可独立验收**（`acceptance` 必填，P-09）——不能等下一片做完才知道这片对不对；
2. **依赖成环即红**（P-11）——A 依赖 B、B 又依赖 A，说明切法错了，不是画图工具的问题；
3. **一片内自带闭环**——来料检验切片把 PC 报告页和 PDA 取样页放在一起，因为只做一个，另一个的数据就是假的。

## 8 命名约定

命名不是审美问题，是**可校验性问题**。`check_contract.py` 的白名单和端判定全靠前缀：

| 对象 | 规则 | 例 |
|---|---|---|
| 模块 | `m-` + 业务域缩写 | `m-iqc` |
| 页面 | `pg-` + 模块 + 任务 | `pg-iqc-report` / `pg-iqc-sample-pda` |
| 命令 | `cap-` + 动词 | `cap-submit-sample` / `cap-approve` |
| 状态机 | `sm-` + 实体 | `sm-inspection` |
| 需求 | `REQ-` + 三位 | `REQ-002` |
| 标注 | `an-` + 三位 | `an-001` |
| 节点 | `n-` + 语义 | `n-table` / `n-btn-submit` |
| 角色 | `u-` + 岗位 | `u-qa` |

页面的 `-pda` 后缀不是装饰：端判定既看 `target` 字段，也建议看后缀——两者不一致是端错配的高发点。

## 9 自查清单

拆完页面，按顺序问这 9 句，任何一句答不上就回去改：

1. 每个页面的 `task` 能不能一句话说完，且不含"和"？
2. 有没有哪条命令被两页 owns？
3. 有没有哪页有两个同等权重的主动作？
4. 每页的四态都能描述出来吗？
5. 详情用抽屉还是页面，是按三条判据定的还是拍脑袋定的？
6. PRD 正文里有没有重复描述组件树的内容？（有就删）
7. 每个判定节点的出边都有 label 吗？
8. 每个切片的页面数、命令数、节点预算都在上限内吗？
9. 切片依赖成环了吗？
