# 需求表达：EARS 六字段与句式模板

> EARS（Easy Approach to Requirements Syntax）原本是五句式模板。这份文档把它和 `requirements[]` 的六个字段一一对齐，目的是让「写需求」和「填 JSON」变成同一个动作——写完就能校验，不需要再翻译一遍。

## 1 为什么用 EARS，不用"用户故事 + 验收标准"

用户故事擅长表达**价值**，不擅长表达**约束**。工业系统的需求 80% 是约束：什么状态下不能做、谁能做、做不了时怎么提示。这些用"作为一个…我希望…以便…"写不出来，只能写成附加条款，最后变成 PRD 后面那张没人看的"业务规则表"。

EARS 强制句式里带**触发条件**和**前置状态**，正好是按钮可用性和状态机需要的输入。

| | 用户故事 | EARS |
|---|---|---|
| 一句话能不能看出"什么时候不行" | 不能 | 能（`If … then` / `While …`） |
| 能不能直接推出按钮置灰 | 不能 | 能（`While` 子句 = `from` 状态） |
| 能不能自动校验 | 不能 | 能（六字段缺一即 ERROR） |
| 表达价值 | 强 | 弱，需另写一句 goal |

结论：**价值用一句 `goal` 说清楚，约束用 EARS 逐条写**。不要试图用一句话同时承担两件事。

## 2 五句式 → 六字段的映射

| EARS 句式 | 模板 | 落到字段 | 校验点 |
|---|---|---|---|
| 通用 Ubiquitous | 系统**应**〈响应〉 | `expectation` | 无触发，全场景成立 |
| 事件驱动 When | **当**〈触发〉时，系统应〈响应〉 | `trigger` + `expectation` | `trigger` 不能为空，且必须是可观测事件 |
| 状态驱动 While | **在**〈状态〉**期间**，系统应〈响应〉 | `stateMachine` 的 `from` | 状态 key 必须在 `sm.states` 内（L2-35） |
| 非期望 If…then | **如果**〈条件〉，**则**系统应〈响应〉 | `acceptance[kind=illegal]` | 每条需求至少 1 条（L2-34） |
| 可选特性 Where | **在**〈特性启用〉**的情况下**，系统应〈响应〉 | `guards[]` 或页面 `variant` | guard 要有 `fallback` |

五种句式不是五种格式，是**五种必须覆盖的语义**。一条需求通常组合 2~3 种：

```
While 单据处于「待审核」，当质量工程师点击审核时，系统应记录审核人并冻结判定。
If 审核人与取样人为同一人，则系统应拒绝并提示「审核人不得为取样人」。
```

这句话里 `While` 给了 `from`，`When` 给了 `trigger`，`If` 给了 `illegal` 验收——一条需求写清了三件事。

## 3 逐字段写法

### `actor` 角色

- 写**岗位**，不写人名、不写"用户"、不写"系统管理员"这种万能角色。
- 必须能对上角色表里的 `是否真实存在 = 是`。
- 一个动作多个角色可做时写数组，但要问一句：这两个角色看到的按钮文案会一样吗？不一样就说明是两条需求。

```json
"actor": ["u-qa"]
```

> 反例：`"actor": ["用户"]`。看到"用户"就该警觉——说明还没想清楚谁站在这个页面前。

### `trigger` 触发

- 必须是**可观测事件**：点击、扫码完成、接口回调、定时到达、状态变更。
- 不能写"需要审核时"这种心理活动，也不能写"系统自动"（那是 system 迁移，不属于人工需求）。

| 反例 | 问题 | 改成 |
|---|---|---|
| 需要看报告时 | 心理活动 | 质量工程师在列表点击「详情」 |
| 数据同步后 | 主语缺失 | ERP 推送入库单成功回调（≤3s） |
| 审核后 | 与 `to` 重复 | 点击「审核」并二次确认 |

### `rule` 规则

- 只写**约束**，不写流程（流程在 `trigger` 和 `stateMachine` 里）。
- 禁止主观词：应该、尽量、合理、友好、快速、适当。
- 每条规则要能被测：能写成"给定 X，则 Y"。

```
合格判定的前置条件：标准模板已生效、取样记录已提交、取样数量 ≥ 标准规定最小值
```

三句话，三条都能测。写成"系统要保证判定正确"就一句都测不了。

### `stateMachine` 状态机

- 格式固定：`sm-xxx：from → to`，`from`/`to` 用状态 key 不用显示名。
- `sm-xxx` 必须真实存在（L2-35 校验）。
- 不改变状态的需求（查询、导出）写 `sm-inspection：不变（approved）`——**不能留空**，留空等于说这个动作不影响任何状态，那就要问它凭什么出现在这个页面上。

```
sm-inspection：reported → approved
sm-inspection：不变（reported / approved）
```

### `expectation` 预期

- **单一响应**。一条需求只描述一个系统响应。
- "系统应保存并提示成功并刷新列表并发送通知"——四个响应，应拆成四条需求或一条需求 + 三个副作用。
- 响应要可观察：页面上能看到什么、接口返回什么、日志里有什么。

### `acceptance` 验收

- 每条需求**至少 1 条 `kind:"illegal"`**（L2-34 硬性）。
- 三种 kind 各自覆盖什么：

| kind | 覆盖 | 例子 |
|---|---|---|
| `happy` | 正常路径 | 状态为待审核、点击审核、审核人非取样人 → 状态变已归档 |
| `illegal` | 非期望路径 | 状态为已归档、点击审核 → 拒绝，提示「仅待审核可审核」 |
| `edge` | 边界 | 批量审核 30 条中第 29 条触发四眼冲突 → 整批退回 |

- `illegal` 至少覆盖三类之一：**状态不符 / 权限不足 / 并发冲突**。只写状态不符的需求，权限和并发一定漏。

## 4 条目结构

```json
{
  "id": "REQ-002",
  "title": "质量工程师审核并归档检验报告",
  "actor": ["u-qa"],
  "trigger": "在待审核报告详情页点击「审核」并在二次确认框中确认",
  "rule": "审核人不得为取样人；标准模板须已生效且报告含限值快照；同一单据并发审核按乐观锁拒绝后到者",
  "stateMachine": "sm-inspection：reported → approved",
  "expectation": "单据状态变为已归档，记录审核人、审核时间与所用标准版本，页面状态条切到「已归档」，「审核」按钮转为不可用",
  "acceptance": [
    { "kind": "happy",   "given": "单据 reported 且审核人≠取样人", "then": "状态置 approved，返回 200" },
    { "kind": "illegal", "given": "审核人＝取样人",                "then": "拒绝，code=EYE_PRINCIPLE，提示「审核人不得为取样人」" },
    { "kind": "illegal", "given": "单据已被他人审核",              "then": "拒绝，code=STALE_VERSION，提示「该单已被 XXX 审核」" },
    { "kind": "edge",    "given": "批量选中 30 条其中 1 条冲突",   "then": "整批退回，逐条列出冲突单据，不做部分成功" }
  ],
  "priority": "P0",
  "pageIds": ["pg-iqc-report"]
}
```

四项注意：

1. `id` 一旦分配不再改。PRD 交叉引用、测试用例编号、缺陷单都靠它。
2. `pageIds` 必须指向真实页面，否则 L2-36 红——这是防止"需求写了但没地方承载"。
3. `priority` 只用 `P0/P1/P2`，不用高/中/低（评审时会全变高）。
4. `acceptance[].given/then` 用短句，不写步骤序列。步骤序列属于测试用例，不属于需求。

## 5 常见写错的五类

| 症状 | 例子 | 病因 | 改法 |
|---|---|---|---|
| 需求其实是方案 | 「系统应提供审核按钮」 | 把 UI 当需求 | 改成「质量工程师应能在不打开取样记录的情况下判断是否放行」——然后按钮只是多种实现之一 |
| 一条需求塞四件事 | 「保存、校验、提示、发通知」 | 没做原子化 | 拆成 4 条，或用 1 条主需求 + 3 条副作用（副作用也要有 acceptance） |
| 状态机写显示名 | `待审核 → 已归档` | 照抄界面文案 | 用 key：`reported → approved`。显示名会变，key 不变 |
| 验收只有 happy | 只写"正常审核通过" | 想着"先写主流程" | 补 illegal，问自己：这个按钮在什么情况下不该亮？ |
| 规则含主观词 | 「系统应友好提示」 | 用形容词代替设计 | 「提示文案包含当前状态名与可执行的前置状态」——可测 |

## 6 一条需求的完成判据

写完自查五项，全过才算写完：

1. `actor` 是岗位，且在角色表里标了"真实存在"；
2. `trigger` 是别人能替你观测到的事件，不是"想审核的时候"；
3. `rule` 里没有一个形容词；
4. `stateMachine` 有明确 from/to（或明确写"不变"）；
5. `acceptance` 里有一条你会拿来当**第一个测试用例**的非法路径。
