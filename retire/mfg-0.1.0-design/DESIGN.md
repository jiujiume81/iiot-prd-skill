## A. 定位与命名

### A.1 目录名

**结论：`mfg-req-analysis`，全小写连字符，放在 `/Users/yuxiufu/WorkBuddy/原型PRD/` 下与 `IIOT-PRD` 平级。**

三条理由：

| 理由 | 说明 |
|---|---|
| `mfg` 而不是 `manufacturing` | 路径短，且在 skill 名里重复出现不影响触发（触发靠 description，不靠目录名） |
| 用 `req-analysis` 而不是 `requirements` | 与 IIOT-PRD 的 description 用词区分开，两个 skill 同时被召回时，模型能按"analysis / PRD"选对 |
| 不用 `six-step` / `method` 这类抽象词 | 用户下次搜"六步法"时，靠 description 里的触发词命中，不靠目录名；目录名要说明**业务域 + 动作** |

拒绝的备选：`mfg-requirement`（单数会被理解成"一条需求"）、`req-six-step`（六步会变，名字不该绑数字）。

### A.3 与 IIOT-PRD 的边界（硬分流，不许两边都做）

| 用户的话 | 进哪个 | 判据 |
|---|---|---|
| "帮我分析一下这个需求" / "业务方到底想要什么" / "这个需求值不值得做" | **本 skill** | 产物里不含页面、按钮、字段、状态机 JSON |
| "明天要开需求评审会" / "帮我想想研发会挑什么刺" | **本 skill** | 交付物是问题清单，不是设计 |
| "给我画个原型" / "出个 PRD" / "给开发做的东西" / "PDA 页面长什么样" | **IIOT-PRD** | 产物必须是 `proto.json` + 容器 + PRD |
| "先分析，分析完再画原型" | **本 skill 做完 → 转 IIOT-PRD** | 用 A.4 的交接表逐列对齐，不重写 |
| "上次分析完了，现在改一版" | 读 `_gate.json` 定位断点，从断掉的步继续 | 不许重开一份新目录 |

**一条铁律**：本 skill 产出六个 `.md` + `_gate.json`，**不含任何 `.json` 契约、不含 HTML、不含页面清单**。出现 `componentTree` / `pages[]` / `capabilities[]` 字样即判越界（`A-65`）。

### A.4 与 IIOT-PRD 的交接（列名逐字对齐，保证 IIOT 能直接吃）

| 本 skill 产物 | IIOT-PRD 对应步 | 交接方式 |
|---|---|---|
| `M1-problem.md` 的「边界与非目标」 | `01-positioning.md` | 非目标表整段复制，一条不改 |
| `M1-problem.md` 的「问题与方案分离」「真问题陈述」 | `02-problem.md` | 原话表 + 证据等级整表复制 |
| `M2-roles.md` 的「角色表」+「角色现实性核对」 | `03-roles.md` | 六列不动；IIOT 把「是否真实存在」「是否同一人」接在右侧，第四条约束转成 `capabilities` 的校验 |
| `M3-scenarios.md` 的「场景表」 | `04-scenarios.md` | 六列顺序不动，追加失败兜底 / 频次 / 受影响角色 |
| `M4-flows.md` 的「主流程」「状态机」 | `05-user-flows.md` | 状态变化列必须是 `X → Y`，IIOT 的 `stateMachines` 直接搬运 |
| `M5-exceptions.md` 的「异常清单」 | `06-exceptions.md` | 类别列必须在第一列，IIOT 的 `G-11` 按行首判类 |
| `M6-review.md` 的四角色 + 5 风险 | `07-review.md` | 风险表按"上线后多久会爆"排序，列名一致 |
| `_gate.json` 的 `nonGoals` / `scale` | `_gate.json` 同名字段 | 字段名逐字相同，可直接合成 |

**为什么现在要对齐**：不对齐，用户分析完转原型时会把六份文档手抄一遍，抄的过程就是丢信息的过程——他上次 QMS 来料模块大改，就是"分析文档里没写先入后检，画原型时也没人想起来"。

## C. 三个产品判断

### C.1 角色表加不加列

**结论：加，但不加在六字段里，另起一张《角色现实性核对》表。**

不改他的六字段，一个字都不改：列名、列序、含义全保留。新增的是**第二张表**，因为六字段回答的是"这个角色在工作里做什么"，新表回答的是"这个角色在系统里是否成立"——两个问题两套字段，混进一张表会被读成"你把我给的结构改了"，而拆开之后六字段可以被脚本逐字比对、一行不改。

**为什么不用合并成 10 列**：合并省一条表头判据，但会把"六字段装不装得下现实性核对"这件事测不出来。实跑（`DRYRUN-qms-incoming.md`）证明六列装得下：取样员与保管员重叠这件事，写在六列角色表的"和其他角色的关系"里也不违和，真正的结论必须另起一行写约束。拆开更贴用户原话。

四列：

| 列名 | 判据 |
|---|---|
| 角色名称 | 必须与第一张表逐字一致 |
| 是否真实存在 | 只允许 `是` / `否（实际由 X 兼任）`；写"是"也要能说出有几个人 |
| 与其他角色是否同一人 | 只允许 `否` / `与 X 同一人（N 人重叠）` |
| 由此产生的系统约束 | 一条可校验规则（要么可做四眼，要么必须允许兼岗），写不出就说明这行是凑的 |

**反例（真发生过）**：QMS 来料检验里设了"质量总监"这一级审批。实际这一级由质量工程师老张兼任。六字段表完全看不出问题——权限、目标、关注信息都对。等到做强制二级审批，所有单子卡在同一个人手上，比线下还慢。这张表只要写一行"质量总监 / 否（由质量工程师老张兼任）/ 与 u-qa 完全同一人（1/1）/ 二级审批必须可关闭，且允许同一账号既提交又审批（放弃四眼）"，这条设计当场就废了。

**第二个反例**：取样员与仓库保管员有 3 人重叠。"取样人不得是收货人"这条规则看着很对，实际落不了地，一落地就有一半单子做不了。真正能做的是"审核人不得是取样人"。这个差别只有在这张表里才看得见。

**如果用户明确说"我就要六列"**：允许，但 M2 必须保留这张核对表并整表填 `N/A`，同时在 `__豁免说明` 那一行写一句原因。脚本对全 `N/A` 报 WARN，不报 ERROR——不强迫，但不许静默跳过。

**为什么这不算不听用户**：他给六字段时说的是"角色识别"，重点是识别出谁在用。他踩过的坑（质量总监是空的、四眼落不了地）正是这张表要抓的。加表不是改结构，是补一个他没提但一定会疼的核对动作。

### C.2 评审加不加第四个角色

**结论：默认加，不问用户。**

理由三条：

1. **问了一定被拒**。他的心智模型里评审就是"研发/测试/业务"三方，问"要不要加现场"他会说不用——不是因为他判断过，而是因为这个词不在他脑子里。
2. **这个角色成本最低、命中率最高**。10 个问题，两分钟能写完；但它抓的是另外三个角色结构性抓不到的东西——前三方都在办公室，现场在车间。
3. **制造业最贵的失败不是"功能不对"**。功能不对，测试能测出来；"上线后现场不用"，任何一个评审环节都测不出来，只有让现场使用者提问才可能提前发现。多一步扫码、按钮戴手套点不到、货场没信号，这三件事决定了系统会不会被纸条绕过。

执行方式：**不问，但告知**。M6 开头写一行：

> 本次按四个角度审：研发 / 测试 / 业务 / 现场使用者。第四个是默认加的——工业系统最常见的死法不是功能不对，是上线后现场不用。你说不要，我删掉，但风险清单里会多一条。

给退出口但不给商量的入口：用户明确说"不要第四方"，M6 的 `## 现场使用者` 节保留，内容写 `waived：用户要求删除，原因：{原话}`，脚本报 WARN（`A-50b`），并在风险表加一条"现场不接受导致绕过系统"。这样"删掉"这个动作本身留下痕迹。

现场使用者的问题必须**只能**落在这些条件上，否则就是研发问题换了个署名：

| 允许的提问角度 | 例子 |
|---|---|
| 手部状态 | 戴棉手套，这个 32px 的按钮点得中吗 |
| 环境 | 货场只有 2 格 4G，这单能不能先存着 |
| 光线与噪音 | 车间 85 分贝，提示音听得见吗 |
| 站位与姿势 | 一手拿 PDA 一手翻货，两只手都不空 |
| 班次 | 夜班只有 1 个人，卡住了找谁 |
| 纸笔与口头 | 这一步不做系统，我用纸条记着行不行 |
| 工具更换 | 换了扫码枪型号，要不要改 |
| 时间压力 | 30 分钟内要卸完一车，你这个流程几步 |

### C.3 场景"穷举"怎么做（本 skill 的核心资产）

**结论："穷举"不可能靠灵感达成，只能靠"每个格子的归属都有交代"。交付的不是"很多场景"，是一张覆盖矩阵。**

定义：`穷举 = 十一维矩阵的每一个 (维度, 取值) 格，都有归属——要么是一个 S 编号，要么是一条排除理由，要么是一条待确认。空格子数为 0。`

#### C.3.1 十一个维度与取值（逐字，脚本按此校验覆盖）

维度编号 `D1~D11` 是内部坐标。**场景表不设 `维度` 列**——一条场景常同时落在两三个轴上（`先入后检 × 交接班`），写成场景的属性就只表达得了一个。维度只出现在**覆盖矩阵**的「维度 / 取值」两列里，那一列才是归属的唯一记录。

| 维度 | 族名（写进表里的） | 封闭取值（穷举轴） |
|---|---|---|
| D1 | `阶段` | 创建前 / 创建 / 待处理 / 处理中 / 待确认 / 已完成 / 已作废 / 归档后 |
| D2 | `触发` | 计划 / 异常 / 手工 / 接口 / 扫码 / 定时 / 导入 / 设备信号 |
| D3 | `批量` | 单条 / 一批 / 多批混选 / 全量 / 拆批 / 并批 / 分批到货 |
| D4 | `来路` | 正常入库 / 退货再入 / 让步接收 / 转库调拨 / 委外回收 / 返工返修 / 试制 / 客户供料 / 紧急放行 |
| D5 | `角色` | 发起 / 执行 / 审核 / 下游等待 / 监管 / 外部方 / 班组长 / 替班 |
| D6 | `结果` | 通过 / 部分成功 / 全失败 / 超时 / 重复 / 越权 / 数据不全 / 断网 |
| D7 | `连续` | 编号连续 / 断号 / 重号 / 跨月跨年 / 一物多码 / 多物一码 / 人为改号 |
| D8 | `版本` | 首建 / 标准换版 / 主数据变更 / 作废重开 / 历史迁移 |
| D9 | `时间` | 白班 / 夜班 / 交接班 / 峰谷 / 跨天 / 月末 / 停产检修 |
| D10 | `现场` | 产线 / 工位 / 车间 / 仓库 / 在途 / 无网 / 戴手套 / 噪音 / 光线 |
| D11 | `形态` | 粉体 / 液体 / 卷材 / 结构件 / 气体 / 其他（取值从物料主数据来，不靠灵感） |

**核心 6 维（`阶段` `触发` `批量` `来路` `角色` `结果`）每个业务对象必扫；扩展 5 维（`连续` `版本` `时间` `现场` `形态`）按对象性质启用**——判断标准：`连续` 只要这个对象有编号就启用；`版本` 只要有"标准/主数据"就启用；`时间` 只要跨班就启用；`现场` 只要不是纯办公室操作就启用。制造业项目实际上 10 维全开，办公室后台功能才会关掉 `现场`；`形态` 是实跑补的第 11 维，凡来料、在制、成品这类有物理形态的对象一律启用。

被关掉的维度不许默认关，必须写进 `_gate.json` 的 `matrix.enabledDims` 并给一条原因，`A-39` 会查。

**本表是唯一源。** `scripts/check_analysis.py` 的 `DIMS` 常量必须与本表**逐字一致**（族名、取值、顺序），偏差一个词，所有项目的 `A-24` 都会红。以本表为准改脚本，不以脚本为准改本表——因为场景表 `维度` 列写的是 `族:值`，族名必须是短词（`阶段:` 能写，`生命周期阶段:` 太长会把列挤爆）。

**总格数**：D1~D10 = 8+8+7+9+8+8+7+5+7+9 = **76**；启用 D11 后 +6 = **82**。实跑（`DRYRUN-qms-incoming.md`）报的是 **78**，因为那次用的是**含两个结论型取值的旧 `来路`（11 值）**。删掉 `先入后检`/`先检后入` 后正好 −2 = 76——**这两个格子本来就该由 Step 2.5 产出，不该占格数**。格数不是指标，归属完整才是；脚本现算，不写死。

#### C.3.2 高危配对表（只跑这 8 组两两交叉，不做全笛卡尔积）

全组合是 8×8×7×11… ≈ 7 亿，不可执行。真正出事的是下面 8 组：

| # | 配对的维 | 交叉点 | 本 skill 必产出的一条场景 |
|---|---|---|---|
| 1 | 交接时序（Step 2.5）× D1 阶段 | 两边的单据谁先建，反过来行不行 | **先入后检 / 先检后入**（用户踩过的坑 1）。**注意：这一条不许写进 D4 的取值表**，见下方"结论型取值"警告 |
| 2 | D7 连续 × D3 批量 | 断号时怎么判定该检哪些批 | **按检验频次抽检，但批次号不连续 → 抽检基准失效**（用户踩过的坑 2） |
| 3 | D3 批量 × D5 角色 | 批量里有一张撞四眼 | 整批退回 / 跳过该张 / 拆成两张单 |
| 4 | D9 时间 × D1 阶段 | 单据停在"处理中"时交班 | 交接班时未提交的单据归谁、算谁的 KPI |
| 5 | D2 触发 × D6 结果 | 设备信号触发但部分成功 | PLC 给了 10 条，系统只收 7 条，另 3 条怎么补 |
| 6 | D10 现场 × D6 结果 | 无网 + 提交失败 | 存本机 / 纸记 / 回办公室补录，补录要不要标"补录" |
| 7 | D8 版本 × D1 阶段 | 换版后看已归档单据 | 历史判定按旧版还是新版、能不能重算 |
| 8 | D5 角色（外部方） × D1 阶段 | 供应商在报告发出前就要结果 | 电话先告知 / 只给结论不给数据 / 拒绝 |

这 8 组里第 1、2 组直接来自用户踩过的坑。但**第 1 组的产出方式在本轮被改了**：

- 早期版本把 `先入后检` / `先检后入` 直接写成 `D4 来路` 的两个取值。实跑（`DRYRUN-qms-incoming.md`）证明这是**循环论证**——把答案写进输入，再从输入里扫出来。
- 现在 `D4` 只保留中性的来路（正常入库/退货再入/让步接收/…/紧急放行），"先后顺序"由 **Step 2.5** 的追问产出。

**结论型取值禁令**：任何维度取值如果是"某条具体场景的名字"，一律不许进词表。判据 `A-24c`：`DIMS` 常量里的取值，不得与本项目场景名重合 ≥4 字。词表只能放**中性轴**（时间/空间/形态/数量/顺序的类别），结论必须下沉到场景库与协议。

#### C.3.3 扫描协议（六步，可机械执行）

```
Step 1 定扫描对象
  从 M1 的原话里抽出业务对象（单据/批次/工单/样品/设备），每个对象扫一遍。
  例：来料检验 → 对象 = 来料批次、检验任务、检验报告。三个对象，扫三轮。

Step 2 单因子扫描（核心 6 维 + 已启用的扩展维）
  固定其余维为"常规值"，把这一维的每个取值走一遍，每个取值问一句：
  "这个取值下，用户会做什么、系统要判断什么？"
  常规值必须写在覆盖矩阵顶部一行，例：来源=正常采购入库、批量=单批、角色=执行人、结果=通过。
  产出：候选场景（先落 _draft/M3-candidates.md，不直接进场景表）。

Step 2.5 跨系统动作时序（本轮补，治"先入后检"这类跨系统顺序问题）
  对每一个"两个系统都有动作"的交接点，问三句：
    ① 两边的单据谁先建？（收货单 vs 检验任务）
    ② 反过来行不行？行的话各自状态变成什么？
    ③ 反过来时，谁有权决定、留什么记录？
  产出：同一件事的"正反两条路"各成一条场景（例：S1 先检后入 / S2 先入后检）。
  这一问不许并进任何维度取值，否则就是"把答案写进输入"。

Step 3 高危配对扫描
  只跑 C.3.2 那 8 组，每组至少产出 1 条候选。产不出来说明 Step 2 扫太浅。

Step 4 归属裁决（关键，不许留空）
  每条候选二选一：
    - 进场景表 → 分配 S 编号，六字段必须填满，填不满的退回 _draft
    - 不进场景表 → 覆盖矩阵里写「排除」+ 一条含具体事实的理由
  实在判断不了的 → 写「待确认」，进待确认清单。待确认 ≤7 条（A-24）。

Step 5 覆盖自检
  统计：总格数 = Σ(每维启用取值数)。
  已归属格数 / 总格数 必须 = 100%（空格即红）。
  待确认格数 ≤ 7。
  排除格数 / 总格数 ≤ 40%（超了说明在偷懒，把该做的场景都"排除"掉了）。
  场景数 ≥ 15，其中 P0 ≥ 5。
```

#### C.3.4 覆盖矩阵怎么写（一件事一行，不许合并）

| 维度 | 取值 | 归属 | 理由 |
|---|---|---|---|
| D1 阶段 | 归档后 | S12 | 客审要 12 个月前的报告，导出要能带出当时的限值快照 |
| D1 阶段 | 已作废 | 排除 | 作废单不做查询入口，只在追溯时按单号穿透（见 M4 §状态机） |
| D4 来路 | 先入后检 | S2 | 急用料先进库、检验结论后补，库存要挂"待检冻结" |
| D4 来路 | 先检后入 | S1 | 常规路径 |
| D7 连续 | 一物多码 | 待确认 | 同一桶料桶身码与托盘码不一致时以哪个为准 |

**「理由」列的硬要求**：排除理由必须含一个具体事实（数字、系统名、单据名、角色名）。写"不适用""业务上不需要""概率低"直接判红（`A-24b`）。理由要能让第三个人复核。

**但 `A-24b` 只能验形，验不了义。** 实跑里出过两条"含具体事实、带 M4/M5 引用、也带数字"却在语义上排错了的：

| 排除写法 | 为什么形式全绿、语义全错 |
|---|---|
| `D1 创建前 / 货未到就没有单据` | 把「检验任务建单前」读成了「到货前」。差的这个状态（货到了、任务没建）正是先入后检 |
| `D10 光线 / 外观漏判主因是油污反光` | 油污反光**就是**光线问题——这条理由在证明该格重要的同时把它排除了 |

**所以排除也要过一句人问**：

> 如果这件事真的发生了，是**哪一格**接住它？

答不出来 → 这条排除是错的。答得出来 → 把那个格号直接写进理由（`超期由 D1 待处理 × D6 超时 承载`），下一个人一眼能核。这条不进脚本，进 `references/03-scenarios.md` 的自检清单。

## D. 制造业领域知识的组织方式

三条原则，先立规矩再给内容：

1. **不写功能，只写边界。** 每个系统只回答"它管什么、不管什么、和谁交接什么"。
2. **只写会断的地方。** 系统的功能描述网上都有，会断的交接点网上没有，只能靠项目积累。
3. **每条都是可检索的条目，不是段落。** 全部表格化，`grep 关键词` 能一行命中。

### D.1 系统地图（13 个系统，各一句话边界）

| 系统 | 管什么（一句话） | 明确不管什么 | 主要上游 | 主要下游 |
|---|---|---|---|---|
| ERP | 订单、采购、库存账、成本、财务 | 不管工序、不管检验判定 | 销售订单、采购申请 | WMS（收货/发货指令）、MES（工单）、QMS（检验委托） |

### D.2 交接点与常见断点（本 skill 最值钱的一张表）

| # | 交接 | 交接物 | 交接字段 | 常见断点 |
|---|---|---|---|---|
| 1 | QMS → WMS | 检验判定结论 | 批次号 / 判定（合格/不合格/让步）/ 判定时间 / 报告号 | **WMS 没有"待检"这个库存状态**，货先进了可用库存，判定出来时已经被领用 |
| 2 | QMS → MES | 工序放行 | 工单号 / 工序号 / 放行结论 | 首件不合格但工单已报工，MES 不知道要停 |
| 3 | LIMS → MES | 样品与工单绑定 | 样品号 / 工单号 / 工序号 / 取样点 / 取样时间 | 样品只登了批次号，没登工单号，追溯时找不到是哪张工单的料 |
| 4 | LIMS → QMS | 检验结果 | 样品号 / 项目 / 实测值 / 单位 / 检出限 / 仪器 | 检出限没传，判定"<0.01"被当成 0.01 存 |
| 5 | SPC 数据源 | 控制图原始值 | 点位 / 时间戳 / 值 / 采集方式 | **从 PLC 采和从检验记录来是两套数**，同一工序两条控制图对不上；采样频率不同，CPK 算出两个值 |
| 6 | MES → WMS | 物料消耗 | 工单号 / 物料 / 批次 / 数量 | 倒冲时批次由系统按 FIFO 猜，实际现场拿的是另一批，账实不符且追溯错 |
| 7 | WMS → MES | 发料 | 发料单 / 批次 / 库位 | 一次发料分多次上料，MES 只记第一次的批次 |
| 8 | ERP → WMS | 收货指令 | 采购单 / 供应商 / 数量 | 超收/短收的容差在 ERP 定，WMS 不知道，收货卡住 |
| 9 | SRM → QMS | 供应商批次与 COA | 供应商批次号 / COA 文件 / 到货时间 | **供应商批次号规则各家不同且会变**，无法用它做抽检频次基准 |
| 10 | APS → MES | 工单与工序计划 | 工单号 / 工序 / 计划起止 / 设备 | 插单后 APS 重排，MES 里已开工的工序不跟着变，两边计划对不上 |
| 11 | MES → APS | 实际进度 | 完工数 / 报废数 / 实际工时 | 报工滞后，APS 按计划推，越推越偏 |
| 12 | EAM → MES | 设备停机 | 设备号 / 停机起止 / 原因码 | 保养时段和工单计划冲突，MES 仍按有设备排产 |
| 13 | MES → EAM | 设备运行 | 运行时长 / 产量 / 报警 | 一台设备做多个工单，运行时长按工单分摊的规则没定 |
| 14 | PLC → MES | 产量计数 | 设备号 / 计数 / 时间 | 一个循环多件、一模多穴，按信号次数算产量必然少算 |
| 15 | PLM → MES | 工艺路线 / BOM 版本 | 物料号 / 版本 / 生效时间 | 变更生效时点在制工单用旧版还是新版，没人定 |
| 16 | ANDON → MES | 停线 / 恢复 | 工位 / 停线原因 / 起止 | 停线期间已报工的产量没扣，OEE 算出来超过 100% |
| 17 | 追溯 ← 全系统 | 批次父子关系 | 父批次 / 子批次 / 转换关系 / 数量 | 拆批、并批、让步接收三种情况下父子关系怎么建，各系统各写一套 |

**用法**：M4 画流程时，每画到一个跨系统步骤，回这张表查一次"这一步的交接物有没有断点"。查到就要在 M5 里落一条异常。

### E.7 M3 闸门：怎么判"用户真的确认过"

这是整个 skill 唯一一个 ERROR 级人工闸门，也是防"模型自签"的核心。**五重校验，缺一红。**

| 重 | 校验 | 判据 | 挡的是什么 |
|---|---|---|---|
| ① 有人 | `confirmations.M3.by` 非空，且不含"AI""模型""助手""Claude""GPT" | 空 / 写"模型已确认" | 模型替用户签字 |
| ② 有时 | `confirmations.M3.at` 是合法 ISO8601，且 ≤ 当前时间 | 未来时间 / 自然语言"刚才" | 伪造时间 |
| ③ 有据 | `confirmations.M3.quote` 是用户原话，≥4 字，且命中任一：含 `S\d` / 含 `D\d` 或维度名 / 含「没遗漏·没有遗漏·无遗漏」/ **去掉口头语**（确认、好的、可以、没问题、继续、同意…）后仍有 ≥2 个业务实词 | quote 只写「确认」「好的」「ok」 | 用一句无信息量的"好"冒充确认 |
| ④ 对版 | `confirmations.M3.contentHash` = 当前 `M3-scenarios.md` 去掉 `## 确认记录` 节后的 sha256 前 12 位 | hash 对不上（确认的是旧版，之后又偷偷改了场景表） | **确认后改内容**——这是 IIOT-PRD 的 mtime 方案挡不住的 |
| ⑤ 未跳步 | `M4-flows.md` 不存在，或其 mtime ≥ `M3.at` | 第 4 步文件早于 M3 确认时间 | 先写完第 4 步再回头补签 |

**为什么用 hash 而不是只看 mtime**：mtime 只要 `touch` 一下就能伪造，而且用户在确认后追加一行说明也会改 mtime，导致误伤。hash 精确对版，且只对场景表正文算，把「确认记录」节排除在外，避免"记录一写就把自己判红"。

**判据之外的一句人问**（五重都能过、语义仍然会错，实跑里出过：`openQuestions` 只改了 `decision` 没改 `text`，四条全张冠李戴，脚本全绿）：

> 这条答案，对得上这个问句吗？

对不上就是记录不可信。`A-25d` 只能查「文本与该表一致」，查不出「这条问句本来就不该配这个答案」——那是人的事。

**五重全绿才放行 M4。** 拦截时脚本输出固定句式，直接可回给用户：

```
M3 闸门未通过：[具体哪一重]。场景表共 23 条，其中 P0 6 条，待确认 4 条。
请回我一句"场景没遗漏，可以继续"，并确认这 4 条待确认怎么定，我再往下做第 4 步。
```

### E.8 全流程通用判据

| 编号 | 判据 | 什么输入让它红 | 级别 |
|---|---|---|---|
| A-60 | `_gate.json` 里 `status=done` 的步，对应文件必须存在 | 标 done 但文件没有 | ERROR |
| A-61 | M(n+1) 的 mtime ≥ M(n) 的 mtime（`M3` 的确认记录追加除外） | 六份文件同一分钟生成（一次性写完，等于没分步） | WARN |

## F. 与用户的交互协议

### F.1 第一轮回复只允许四件事

```
1. 我听到的原话（逐字引用，不加解释，≥3 条）
2. 我推出的目标与损失（每条标 stated / inferred / measured）
3. 这次不做的事（3~5 条非目标假设，每条指向一个会被砍掉的功能）
4. 需要你回答的问题（≤3 个，每个都是封闭问题）
```

**禁止**：给方案、给页面、给字段、给结论、写"我建议做成……"、写"整体架构"。

**为什么这么硬**：用户是做产品的人，他给的第一句话里 80% 是方案。第一轮就给方案，等于承认他给的方案是对的，后面五步就变成给这个方案找理由。

自检：第一轮回复里如果出现"页面""按钮""字段""模块""功能"任一，重写。

### F.2 M3 确认单：三分钟拍板的写法

场景表可能有 23 条，倒给用户他不会看。确认单**只给三类东西**，控制在 7 条以内：

```markdown
### 场景拆完了，要你拍 4 件事，3 分钟够

**一、我按十个维度扫了一遍，一共 23 条场景，其中 P0 6 条**（挡住生产的 6 条：

S1 现场取样 / S2 审核判定 / S5 不合格处置 / S9 让步接收 / S11 报告交付 / S14 标准换版后重判）

**二、有 4 处我拿不准，你一句话就能定**（不定的话我按建议先做，改起来要返工）：

| # | 拿不准的 | 我的建议 | 你不定会怎样 |
|---|---|---|---|
| Q1 | 交接班时上一班没提交的单据算谁的 | 算提交人，跨班不转移 | 交接班会有单子卡在两班之间，谁都不认 |
| Q2 | 供应商批次号断号时按什么抽检 | 按收货流水号抽，不按供应商批次号 | 抽检基准失效，可能漏检也可能重复检 |
| Q3 | 让步接收的批在追溯里要不要单独标 | 要，独立状态不并入合格 | 客户查到会整批退货 |
| Q4 | 导出超过 2000 行走异步还是直接下 | 异步给链接 | 月底集中导出会超时 |

**三、这三个我替你定了，你不反对就这么执行**：
1. 检验标准由技术部用 Excel 维护，系统只导入和冻结版本（不做在线编制）
2. 供应商本期无系统账号，只收 PDF（不做在线确认）
3. 控制图数据只取一个源：检验记录（不从 PLC 采）

**回我一句就行**：上面 4 条怎么定 + 场景有没有漏。回"没遗漏，按你说的做"我就开始画流程。
```

三条硬规则：

1. **P0 场景必须点名列出**（不超过 6 个），让他看见"哪些是挡生产的"。全列 23 条等于没列。
2. **待确认 ≤7 条，每条自带建议和后果**。只给问题不给建议，是把判断工作推回去。
3. **默认值单独一段**，写清"现在说还来得及"。不列默认值，评审时会被问"你怎么知道我车间叫什么"。

### F.3 状态记录：`_gate.json` 字段设计

路径：`analysis/<产品>/_gate.json`。这一个文件是唯一的进度真相，模型不许凭记忆说"上次做到第几步"。

|---|---|---|
| `steps[].status` | pending / in_progress / done / blocked | 标 done 但文件不存在 → `A-60` 红 |

| `waived.reviewRoles` | 第四角色的退出口 | waived=true 且无 reason → 红 |
| `openQuestions` | 待确认项，M3 确认后必须全部 `resolved` 或 `assumed`。**`text` 与 `suggest` 必须与 `M3 待确认清单` 同号行逐字相等**（`A-25d`） | 有 `open` 就进第 4 步 → 红；只改 `decision` 不改 `text` → `A-25d` 红 |

**卡点定义**（三道，编号与文件同名同号：`M3` 确认的就是 `M3-scenarios.md`）：

| 卡点 | 位置 | 级别 | 拦什么 |
|---|---|---|---|
| **M1** | 第 1 步完成 → 第 2 步开始 | WARN | 没确认方向就拆场景，等于给方案找理由 |
| **M3** | 第 3 步完成 → 第 4 步开始 | **ERROR 硬闸门** | 用户没确认场景没遗漏就画流程，流程一定漏 |
| **M6** | 第 6 步完成 | WARN | 分析结论没被业务方看过，等于六篇作文 |

### F.4 跨会话恢复

用户不会一次做完六步。每次进入这个 skill，第一步动作固定是：

```bash
python3 scripts/check_analysis.py analysis/<产品>/ --status
```

输出 `_gate.json` 的 `steps` + 未通过的闸门 + `openQuestions`，然后只做一件事：**从第一个非 done 的步继续，或从第一个未过的闸门重问**。不许重开目录，不许凭记忆续写。

## G. 失败模式清单

| # | 表现 | 为什么会这样 | 用什么判据拦住 |
|---|---|---|---|
| F-01 | 场景表写成功能清单（"检验管理""报表管理""基础数据维护"） | 模型把"用户想要什么功能"当成"场景"，因为功能词最容易从需求原文里抄 | `A-21` 场景名含实现名词即红（报表/报告按白名单降 WARN）；`A-22` 触发时机/当前状态写不出就红 |
| F-02 | 把用户给的第一句话直接当结论，六步变成给方案做论证 | 用户的第一句话 80% 是方案；模型顺着说最省力 | `A-03` 判定为"方案"的必须 ≥2 条——全部判成"问题"说明没分离 |
| F-03 | 覆盖矩阵造假：整片整片填"不适用""业务上不需要" | 填"排除"比想场景便宜，且看起来矩阵是满的 | `A-24` 排除占比 ≤40%；`A-24b` 排除理由必须含具体事实 |
| F-04 | 闸门自签：模型自己写 `confirmed: true, by: "用户"` | 用户半天不回，模型想推进 | `A-25` 五重校验：quote 必须含具体对象词，hash 必须对版 |
| F-05 | 用户说"确认"之后又偷偷改了场景表，然后直接画流程 | 改起来很方便，且没人会回头看 | `A-25` 第④重 contentHash 对版，唯一能挡住的一种 |
| F-06 | 流程写成"然后系统处理""提交后状态更新" | 这种句子在任何流程里都成立，写起来零成本 | `A-30` 状态变化必须匹配 `X → Y` 且两端都在状态集里 |
| F-07 | 异常表写成"网络异常 → 提示用户重试" | 这是通用软件套路，不涉及业务后果 | `A-41` 影响必须量化；`A-42` 处理建议必须含降级动作 |
| F-08 | 评审变成夸奖和清单罗列（"建议加强权限校验""注意性能"） | 模型被训练成"有帮助"，而挑刺是"不友好"的行为 | `A-51` 每条必须疑问句 + 点名对象；`A-52` 含"建议/优化/提升"且无问号即红 |
| F-09 | 六份文档写得漂亮，但不说这个需求该不该做 | 分析文档的默认期待是"全面"，不是"有立场" | `A-05` 立场节必须三选一；`A-54` 结论必须"能开工/不能开工" |
| F-10 | 场景越拆越多，60 条倒给用户，用户不看了 | "尽可能穷举"被执行成"尽可能多"，数量代替了覆盖 | `A-26` 待确认 ≤7；确认单只列 P0（F.2） |
| F-11 | 只做主线角色，场景里只有发起人 | 一条主线的流程最顺，写起来最快 | `A-23` P0 场景必须有"受影响角色"；`A-13` 缺席角色 ≥2 |
| F-12 | 一次把六份文件全写完（同一分钟落盘） | 用户给了完整信息，模型想一次交付 | `A-61` mtime 递增校验，WARN 提示"没分步" |
| F-13 | 越界：分析文档里长出页面清单、字段清单、proto.json | 模型默认"帮到底" | `A-63` 出现契约层关键字即红 |
| F-14 | 用"建议考虑""视情况"这类话糊过去 | 拿不准又不想暴露 | `A-62` 出现即红 |
| F-15 | 领域知识写成百科全书，2000 行没人读 | 想显得专业 | 结构化硬约束：D.2/D.3 每条必须一行表格，超过两行的段落即删 |
