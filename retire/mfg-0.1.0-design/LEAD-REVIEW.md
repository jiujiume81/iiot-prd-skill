# 主控复验清单（E 系列判据）

> 这份清单是收尾时我自己要逐条跑的，不采信队友自报。E = 验收（Evaluation）。

| 编号 | 检查什么 | 怎么判 | 不过关的后果 |
|---|---|---|---|
| E-01 | **触发词不打架** | 新 skill 的 description 里不得出现「画原型 / 高保真 / EARS / 契约 / 组件树」；必须出现「只做分析 / 不出原型 / 六步」；且显式写「要出原型/PRD 请用 IIOT-PRD」 | 用户说「分析下这个需求」时两个 skill 抢触发，模型可能直接开始画页面 |
| E-02 | **六步与用户原话对齐** | 用户原话的字段逐字比对：第二步 6 项、第三步 6 项、第五步 8 类 + 4 列、第六步 3 角色 × ≥10 问 + 5 风险。少一项就是没按需求做 | 用户拿到手发现「我要的字段被改了」 |
| E-03 | **加列是加列，不是替换** | 若角色表/场景表加了补充列，用户给的原始字段必须**全在且顺序在前**，补充列只能在右侧并明确标注「建议列」 | 尊重用户结构，否则等于擅自改需求 |
| E-04 | **三步闸门真的拦得住** | 造红：手改 M4 文件 mtime 早于 `_gate.json` 的 M3 确认时间 → 跑脚本必须报 ERROR；删掉 `_gate.json` 的 M3 确认 → 必须报「未确认不许进第四步」 | 闸门形同虚设，模型会自己说「已确认」然后一路写到底 |
| E-05 | **穷举矩阵可机械执行** | 矩阵每一维都要有「怎么扫」的动作描述，不能只列维度名。抽查：任取一个真实需求（用来料检先入后检），能否按矩阵在 10 分钟内扫出 ≥15 个场景 | 「穷举」变成口号，还是靠灵感，还是漏 |
| E-06 | **领域清单是真场景** | 抽查场景库 10 条，每条必须能说出「谁在什么时候做什么、容易漏在哪」；出现「生产管理」「质量管理」这类模块名即判不合格 | 变成百科目录，对分析零帮助 |
| E-07 | **踩坑案例有归因** | 用户给的两个案例（先入后检 / 批次号不连续）必须在库里，且归因到「第几步没做」，不是复述现象 | 案例只当故事看，下次照旧踩 |
| E-08 | **脚本零依赖可跑** | `python3 scripts/check_report.py <dir>`，只用标准库，macOS 自带 python3 直接跑通；退出码 0/1 语义正确 | 用户换台机器就跑不了 |
| E-09 | **skill 能被扫到** | `~/.workbuddy/skills/mfg-req-analysis` 软链指向项目目录；`ls -l` 确认；SKILL.md frontmatter 有 name/description/agent_created | 装了等于没装 |
| E-10 | **模板能直接抄** | `assets/templates/` 六份模板每份都带一行示例行（真实内容，不是 `xxx`），用户复制后知道怎么填 | 模板变空壳，还得自己想格式 |
| E-11 | **单份 SKILL.md 不超过 5k 词** | `wc -w`，超了就把细节赶进 references | 违反渐进披露，skill 一加载就吃满上下文 |
| E-12 | **不碰已封版资产** | `git -C IIOT-PRD status --porcelain` 必须为空 | 把 v0.9.0 改坏了 |

## 交付时必须回答用户的四件事

1. skill 叫什么、装在哪、怎么触发（给一句能直接说的话）。
2. 六步里哪一步是硬卡点，卡点怎么记录（防我自己说「已确认」）。
3. 我替他做了哪几个产品判断（加列 / 第四角色 / 穷举矩阵），每个判断的反例是什么。
4. 怎么验证它真的有用（造红结果，不是「已测试」三个字）。
