## 1 既有资产勘察

### 1.1 SKILL.md 的 frontmatter 规律

| 字段 | 是否必填 | 写法规律 | 本 skill 取值 |
|---|---|---|---|
| `name` | 必填 | 与目录名**完全一致**（`IIOT-PRD` / `XX-PRD` 都是） | `mfg-req-analysis` |
| `version` | 本仓库惯例必填 | 纯 semver，与 CHANGELOG/提交前缀对齐（v0.9.0 / v0.11.0） | `0.1.0` |
| `description` | 必填 | 单行、不换行、四段式：**①定位句（是什么+给谁）→ ②能力句（产出什么、带什么约束）→ ③"当用户要…时使用"→ ④`触发词：`+顿号分隔 20~40 个词** | 见下方骨架 |

`description` 是唯一被模型用来自动选 skill 的文本，写法上有三条硬规律（从 IIOT 21.5KB 与 XX-PRD 里提炼）：

1. **定位句带行业词**（"工业互联网产品经理""制造业智能工厂"），不是泛化的"产品经理"；
2. **能力句里塞可验证的约束**（IIOT 写"由脚本校验""必须真点得动"），让模型知道这不是纯文档模板；
3. **触发词要覆盖同义说法**（"需求分析/需求澄清/调研/访谈/立项"是同一件事的四种叫法），否则用户换个词就选不中。

本 skill 的 description 草稿：

```
name: mfg-req-analysis
version: 0.1.0
description: 制造业智能工厂的需求分析工作台。把「车间一句话痛点 / 一份设备清单 / 一次现场走访」收敛成六份可校验的需求文档（目标边界、真问题、角色岗位、场景流程、异常兜底、评审范围），强制按产线/工位/班次/设备维度穷举场景，场景必须写失败兜底与量化频次，四道里程碑（M1 目标 / M2 真问题 / M3 场景与流程 / M4 范围终审）必须由人签署、由脚本校验文件时间与指纹，防"模型自称已确认"。只做需求侧，不写 PRD、不画原型，往下走移交 IIOT-PRD。当用户要做智能工厂/数字化车间/MES/WMS/QMS/设备联网/产线追溯的需求调研、需求分析、现状摸底、立项材料、需求报告、甲方访谈提纲时使用。触发词：智能工厂、数字化车间、制造业需求分析、需求调研、现状摸底、MES、WMS、QMS、设备联网、产线追溯、OEE、工单、报工、批次追溯、立项、需求报告、访谈提纲、六步法。
```

### 1.2 `check_gate.py` 解剖（452 行，实际 19.9KB）

| 层 | 位置 | 做法 | 可复用性 |
|---|---|---|---|
| 常量 | `:26` `E, W` / `:27` `issues` | 全局列表，`add(level, code, msg)` 三元组 | **照抄**，输出格式依赖它 |
| 步骤定义 | `:36-79` `STEPS` | 每步 `{no,key,file,title,need[],why}`；`need` 是小节关键词，`why` 是报错时附带的人话理由 | **重写数据，照抄结构**（`why` 字段是好设计：错误消息自带"为什么这条必须存在"） |
| 闸门定义 | `:81-85` `GATES` | `(id, 名称, 依赖步 keys, 未确认时的理由)` | 重写（本 skill 是 M1~M4） |
| 枚举定义 | `:88-102` `EXC_CLASSES` / `REVIEW_ROLES` | `(类别名, [命中关键词列表])`，按关键词归并 | 重写（制造业异常分类不同） |
| 文档解析 | `:110` `sections(md)` | 只认 `^##\s+`，返回 `{标题: 正文}`；**剔除 `>` 开头的行** | **照抄，一个字不改**（见下方"为什么"） |
| 小节查找 | `:133` `find_sec(secs, kw)` | 子串匹配标题，首个命中 | 照抄（新脚本可加"多个命中报 WARN"） |
| 表格行数 | `:140` `table_rows(block)` | 数 `|` 开头行，跳过 `^\|[\s:\-|]+\|$` 分隔线，减表头 | 照抄 |
| 表头提取 | `:160` `header_of(block)` | 取第一个 `|` 开头的行，返回原始字符串 | **保留函数，判据改逐字比对** |
| 列表项计数 | `:155` `list_items(block)` | 正则 `^\s*(?:\d{1,2}[.、)]|[-*+]\s)\s*\S` | 照抄 |
| 时间解析 | `:170` `parse_time(s)` | `fromisoformat` 替 `Z`，naive 按本地时区补 aware | **照抄**（时区坑已踩过） |
| 主检查 | `:184` `check()` | 顺序：闸门文件 → 版本 → 步骤覆盖 → 逐步文件+小节 → 非目标/量级 → 卡点签署 → 顺序倒挂 → 各类覆盖率 | 结构照抄，条目重写 |
| mtime 判据 | `:252-258` `G-10` | `getmtime` → UTC aware，与 `A3.at` 比，报差值秒数 | **改造**：多文件 × 多里程碑，加指纹层 |
| 生成骨架 | `:380` `init()` | 写 `_gate.json` + 六个 md，每份按 `need` 生成 `## 小节` + `（待填）` + 末尾 `>` 解释行 | **改造**：从 `SPEC` 生成六份，模板落 `assets/templates/` |
| 入口 | `:412` `main()` | `--init` / `--proto` / 位置参数；docstring 即 `--help` | 照抄约定，去掉 `--proto` |
| 输出 | `:440-448` | `[ERROR] G-05   …` 定宽对齐 + 分隔线 + `ERROR=n WARN=n 放行/拦截` | **照抄格式**（人眼扫得快） |
| 退出码 | `:448` | `0` 放行 / `1` 拦截 / `2` 用法错误 | 照抄 |

**`sections()` 剔 `>` 行是本轮最该抄的一处**（`:114` 注释写得很清楚）：模板每节末尾都带一句「这一节为什么必须存在：…」，不剔掉，判据会被自己的注释满足。**判据不能读自己的注释**——这是闸门类脚本最大的假绿来源。

**`G-10` 的三个已知弱点**（我们不再犯）：

| 弱点 | 现象 | 新方案 |
|---|---|---|
| mtime 会被抹平 | `cp -r`、`git checkout`、解压后全部文件同一秒，判据恒绿 | 加 `A-35` 指纹：确认时快照已存在文件的 sha256 |
| 只比单个文件 | 只查 `proto` vs `A3`，其它产物提前写不拦 | `A-31` 按"文件 × 放行它的里程碑"逐个比 |
| 不拦未来时间 | `at` 写成明年，永远晚于 mtime，判据恒绿 | `A-33` `at > now + 5min` 直接 ERROR |

### 1.3 `_gate.json` 结构（IIOT 样例）

```json
{
  "gateVersion": "1.0",
  "product": "新锂想质量管理系统 · 来料检验",
  "protoFile": "../example-01-qms-incoming.proto.json",
  "steps": [{ "no": 0, "key": "positioning", "file": "01-positioning.md", "status": "done" }],
  "nonGoals": ["…5 条…"],
  "scale": { "records": 9407, "dailyNew": 100, "batchSize": [1, 3], "note": "…" },
  "confirmations": {
    "A1": { "confirmed": true, "by": "俞秀福（产品）· 王工（质量部经理）", "at": "2026-10-29T16:20:00+08:00", "decision": "…" }
  }
}
```

三条设计要点值得继承：

1. **`steps[].status` 与磁盘状态互为证据**（`:216`：标了 `done` 但文件不存在 → "虚报进度"，直接 ERROR）；
2. **`confirmations[].by` 必须是人**，无签署人的确认等于没确认（`:243`）；
3. **`decision` 写"确认了什么"**，不是写"已确认"——事后追责看的是这一句。

## 2 复用 vs 重写

### 2.1 逐段判定

| check_gate.py 片段 | 行数 | 判定 | 说明 |
|---|---|---|---|
| `read / sections / find_sec / header_of / table_rows / list_items / parse_time` | 约 90 行 | **直接复制** | 纯函数、无依赖、造红验证过；跨 skill 共享的唯一代价是重复 90 行 |
| `add / issues / main 的输出与退出码` | 约 30 行 | **照抄约定** | 用户和我们都习惯了这套输出，换格式等于每次重新认 |
| `--init` 骨架生成思路 | 约 30 行 | **改造** | 从 `SPEC` 单一数据源生成，模板落盘到 `assets/templates/` 而不是每次写字符串 |
| `STEPS / GATES / EXC_CLASSES` 数据 | 约 60 行 | **重写** | 六步、M1~M4、制造业异常 12 类全不一样 |
| 小节存在性判据 | — | **重写** | 本 skill 要"小节必须按顺序、且不许只以 `###` 出现" |
| 表头判据 | `:346` | **重写，且是重点** | 由关键词包含改为 split + strip + 逐字列表比对 |
| mtime 判据 | `:252` | **改造** | 单点 → 矩阵（文件 × 里程碑）+ 指纹 + 未来时间 |
| `--proto` 与 G-23/G-24 | 约 15 行 | **删除** | 本 skill 不产 JSON 契约，留 `--proto` 只会让人误以为这里能出原型 |

### 2.2 结论：独立 `scripts/check_report.py`，不抽公共模块

| 选项 | 代价 | 判定 |
|---|---|---|
| A. 抽 `mdcheck.py` 放公共位置（如 `~/.workbuddy/skills/_shared/`） | 两个 skill 靠 symlink 独立安装：单装一份、拷走一份、发给同事一份，全部 `ImportError`；且 `_shared` 目录不是合法 skill，会在 skill 列表里报错或忽略 | ❌ |
| B. `mfg-req-analysis/scripts/` 里反向 import `IIOT-PRD/scripts/check_gate.py` | 跨目录相对路径 + IIOT 目录 gitignore/rename 就断；而且会把"IIOT 的判据"和"本 skill 的判据"绑在一起，改一边炸两边 | ❌ |
| C. **独立脚本，复制 90 行纯函数** | 重复 90 行；将来两边都要改的 bug（如 ISO 时间解析）要改两处 | ✅ |

选 C。理由排序：

1. **独立性 > DRY**：skill 是可分发单元，交付边界就是目录边界，跨目录依赖会让"拷走即用"失效；
2. **封版约束**：IIOT-PRD 是 v0.9.0 封版资产，抽公共模块必然要改它，违反冻结；
3. **演进方向不同**：IIOT 的脚本要吃 JSON/DOM（`check_contract.py` 70KB、`check_interact.py` 79KB），本脚本终生只读 markdown + 一个 json，依赖面差一个数量级，硬合并只会让本脚本背上不需要的东西；
4. 90 行重复的维护成本，低于任何一次 `ImportError` 的排查成本。

> 万一将来真要收敛：在**各自 skill 内部**建 `mdcheck.py`，两个 skill 各存一份同名文件，靠"内容哈希一致"保证同步（`A-52` 之外再加一条自检也行）。现在不做。

### 3.2 场景维度词表（`A-40` 的判据基础）

`维度` 列的写法固定为 `族:标签`，多值用 `、` 分隔（例：`时间:交接班、空间:工位`）。**五族一个都不能空**：

| 族 | 允许的标签（可扩展，但族必须命中） | 为什么这一族不能空 |
|---|---|---|
| `时间` | 班次 / 交接班 / 峰谷 / 月末 / 停产检修 | 制造业的坑一半在交接班：上一班记了半截，下一班不知道 |
| `空间` | 产线 / 工位 / 车间 / 仓库 / 在途 | 同一个动作在工位和仓库的交互完全不同（站着戴手套 vs 坐着双屏） |
| `对象` | 物料 / 设备 / 人员 / 工单 / 载具 | 决定主数据从哪来、追溯链挂在哪 |
| `触发` | 计划 / 异常 / 手工 / 接口 | 只写"正常生产"的场景，等于只写了 30% 的现场 |
| `约束` | 网络 / 权限 / 合规 / 环境 | 车间断网、油污反光、GMP/追溯合规，都是需求不是借口 |

### 3.3 制造业异常 12 类（`A-44`）

软件 8 类沿用 IIOT，工业侧从 3 类扩到 4 类——**设备与工艺**必须拆开：设备故障是硬件问题（备件、点检、维修工单），工艺偏差是参数/配方问题（首件、SPC、参数越界），产品侧处理方式完全不同。

| # | 类别 | 典型 |
|---|---|---|
| 1 | 用户操作 | 报工数量填错、误点首件确认 |
| 2 | 系统状态 | 工单卡在"生产中"、设备状态与系统不一致 |
| 3 | 数据异常 | 批次号重号、物料主数据缺失 |
| 4 | 权限 | 操作工改工艺参数、自己审自己的首件 |
| 5 | 网络接口 | 车间断网、ERP/MES 接口超时 |
| 6 | 并发与重复 | 两人同时报同一工单、扫码重复提交 |
| 7 | 历史兼容 | 老系统工单迁移、旧批次追溯断链 |
| 8 | 运营后台 | 主数据误改、班次配置错 |
| 9 | **设备与硬件** | 扫码枪/电子秤/PLC/网关离线、标签磨损 |
| 10 | **工艺与配方** | 参数越界、版本错发、首件未确认就批量 |
| 11 | 追溯断链 | 上工序未记录、载具与批次对不上 |
| 12 | 标准与版本 | 检验标准/工艺文件改版，历史单据按哪版 |

## 4 判据表（39 条）

级别：`E`=ERROR（拦截，退出码 1）/ `W`=WARN（放行但列出）。每条都必须能回答"什么输入能让它红"。

### 4.1 骨架与齐全性（A-01~A-06）

| 编号 | 检查对象 | 判据（可执行口径） | 级别 | 什么输入能让它红 |
|---|---|---|---|---|
| A-01 | 目录与闸门文件 | `<dir>/_gate.json` 不存在 → 报错并提示 `--init`，**立即 return**，不再往下查（避免一个空目录刷出 30 条噪声） | E | 空目录直接跑 |

### 4.3 表头逐字一致（A-20~A-24，本方案的重点）

| 编号 | 检查对象 | 判据 | 级别 | 红法 |
|---|---|---|---|---|
| A-20 | 表格可解析 | `SPEC` 指定的每张表：小节存在且能取到表头行；取不到 → 报"该小节里没有表格" | E | 场景表写成无序列表 |
| A-21 | **列名逐字一致** | `cells = [c.strip() for c in line.strip().strip("|").split("|")]`，与 `SPEC` 的列名列表**逐个比**（数量、内容、顺序都要一致）。缺列/多列/改名/换位分别报一条，并给 diff：`缺：失败兜底；多：兜底方案；顺序：维度↔优先级` | E | 「失败兜底」写成「兜底方案」/「失败处理」 |
| A-22 | 表头归一化 | 比对前把 `｜`→`|`、NBSP→空格、全角括号→半角；**归一化发生过** → 报"表头含全角字符" | W | 表头用 `｜` 全角竖线 |
| A-23 | 表格行数下限 | 数据行 ≥ `SPEC` 的 `minRows`：场景表 ≥8、异常表 ≥12、角色表 ≥4、风险表 ≥5、原话表 ≥3、路径表 ≥3、指标表 ≥3、范围表 ≥1 | E | 场景表只写 4 行 |
| A-24 | 空单元格 | 数据行里出现连续 `| |`（或单元格 strip 后为空）→ 报行列号，**每表最多报 5 处** | W | 场景「失败兜底」列留空 |

**A-21 为什么必须是列表比对、不能用 `in`**：

```python
# check_gate.py:346 —— 现行写法
if "兜底" not in header_of(sec):        # 「兜底方案」「兜底措施」全过
    add(E, "G-20", "...")

# check_report.py —— 新写法
miss, extra, bad_order = cmp_header(cells, SPEC["04"]["tables"][0]["cols"])
if miss or extra or bad_order: ...
```

同一类假绿在 IIOT 里还有 `:337-340`（角色表只查 `"真实"` / `"同一人"` 两个子串，`是否真实存在（是/否）` 和 `是否真实存在?` 都能过）。本 skill 的表头是全链路下游（人写、模型改、评审读）唯一的锚，必须逐字。

### 4.4 闸门与签署（A-30~A-36）

| 编号 | 检查对象 | 判据 | 级别 | 红法 |
|---|---|---|---|---|
| A-30 | `_gate.json` 结构 | `gateVersion == "1.0"`；`skill == "mfg-req-analysis"`；`project` 非空；`steps` 恰 6 条且 `no` 覆盖 1~6；`metrics` 是数组 | E | 手写 `_gate.json` 漏了 `skill` |
| A-31 | 卡点未确认 | `confirmations` 里 M1~M4 逐个查 `confirmed is True`，未确认各报一条（带该卡点"漏了会怎样"） | E | 只签了 M1/M2 |
| A-32 | 无签署人 | 已确认但 `by` 或 `at` 为空 → "无签署人的确认等于没确认" | E | `confirmed:true, by:""` |
| A-33 | 时间不可信 | `at` 解析失败，或 `at > now + 300s` → "确认时间在未来，判据会恒绿" | E | `at` 写成 `2027-01-01` |
| A-34 | **顺序倒挂（mtime）** | 对 §3 表里每个"文件 × 放行里程碑"：`mtime(file) < at(里程碑)` → 报差值秒数 + "属事后补签"。**核心一条：`05/06` 的 mtime 必须晚于 `M3.at`** | E | `touch -t 202611101200 05-exceptions.md`，M3 签在 12:30 |
| A-35 | **顺序倒挂（指纹）** | `confirmations[Mi].files` 是"确认那一刻已存在文件"的 `{文件名: sha256}` 快照。若**后阶段**文件出现在 `M3.files` 里且内容未变 → "M3 确认前该文件已写完（指纹命中）"。快照缺失 → "未记录指纹，只能靠 mtime" | E（命中）/ W（缺快照） | 先写完 05/06，再用 `--confirm M3` 记录快照，之后不再改这两个文件 |
| A-36 | mtime 全同 | 六份文件 mtime 两两差 < 2s → "疑似整体复制/解压，mtime 不可信，请以 A-35 为准" | W | `cp -r` 一份样例目录后改内容 |

**A-35 的诚实边界**：它拦不住"确认后把文件原样重写一遍"（重写会改 mtime，也改不了内容哈希——所以反而拦得住；真正拦不住的是"确认后重写内容且内容变好"，那本来就是正常迭代）。它拦的是最常见的一种作弊：**六份文档一次性生成完，然后再补 `_gate.json` 的时间**。这种情况下 `M3.files` 快照里必然包含 `05/06`，一抓一个准。

## 7 `check_report.py` 实现要点

### 7.1 函数清单

| 函数 | 来源 | 作用 |
|---|---|---|
| `read / sections / find_sec / header_of / table_rows / list_items / parse_time` | 复制 `check_gate.py:105-180` | 原样不动，连注释一起抄（注释解释了为什么剔 `>` 行） |
| `cells(line)` | 新增 | `line.strip().strip("|").split("|")` → `[c.strip() for c in …]` |
| `norm(s)` | 新增 | 全角→半角、NBSP→空格、去首尾空白；返回 `(归一化结果, 是否发生过替换)` |
| `cmp_header(actual, expect)` | 新增 | 返回 `(missing, extra, misordered)`；**先比长度再比逐项**，避免"换位"被误报成"改名" |
| `digest(path)` | 新增 | `hashlib.sha256(open(p,'rb').read()).hexdigest()[:16]` |
| `check(dir)` | 改造 `check_gate.py:184` | 按 A-01 → … → A-52 顺序执行，早退只在 A-01 |
| `init(dir, project)` | 改造 `:380` | 从 `SPEC` 生成六份 + `_gate.json` |
| `confirm(dir, mid, by, decision)` | 新增 | 写 `confirmed/by/at` + 六份文件 `files` 快照 |
| `print_spec()` | 新增 | 把 SPEC 打成 markdown 表，供 SKILL.md 粘贴（防文档与代码漂移） |
| `main()` | 改造 `:412` | 子命令风格：`check`（默认）/ `--init` / `--confirm` / `--spec` / `--strict`（WARN 也算失败） |

### 7.2 解析坑（写代码时逐条对照）

| 坑 | 后果 | 做法 |
|---|---|---|
| 不剔 `>` 引用块 | 模板自带的解释文字让判据恒绿 | 抄 `sections()`，不改 |
| 表头不 strip 单元格 | 尾随空格、`| ` 缩进导致逐字比对恒红 | `cells()` 里逐个 `.strip()` |
| 用 `in` 判列名 | 「兜底方案」通过「兜底」判据 | `cmp_header` 列表比对 |
| 分隔线正则太严 | 表格用 `|:---|---:|` 时被当成数据行，行数多 1 | 沿用 `^\|[\s:\-|]+\|$`（已容忍 `:`） |
| mtime 用本地时间直接比 | 差 8 小时，判据随机红绿 | `datetime.fromtimestamp(mt, tz=timezone.utc)` 与 aware 时间比 |
| 扫描目录时把 `examples/`、`_design/` 扫进来 | 拿样例去校验样例 | 只校验显式传入的目录，不做递归发现 |
| 一个空目录刷 30 条 | 用户看不到真正的第一条 | `A-01` 命中即 `return` |

- 退出码：`0` 放行 / `1` 拦截 / `2` 用法错误（与 `check_gate.py` 一致）；
- 行尾必须打**判据总数与实装级别分布**——`SKILL.md` 里报的条数由此对齐，避免"文档写 39、实际 31"。
