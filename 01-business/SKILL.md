# 业务分析（第 1 段）

只回答三个问题：**该不该做、谁在里头、有多少种情况**。三个问题没答案，后面写什么都是给假设镶边。

> **路径约定**：`$SUITE` = 套件根（同时含 `01-business/`、`02-requirement/`、`03-prototype/`、`shared/` 的那一层）。
> 每个会话定位一次：`SUITE=$(cd "$(dirname "<本 SKILL.md 的绝对路径>")/.." && pwd)`。
> **不要用 `../`**——脚本用 `abspath(__file__)` 找 `shared/`，软链调用时不解析软链。

## 一、先判我在哪一段

先看文件，不看记忆：

| 现场 | 判定 | 动作 |
|---|---|---|
| 目录里没有 `_state.json` | 全新项目 | `--init` 起骨架，从 S1 开始 |
| `stage = 1` | 本段，可能做到一半 | 从第一个非 `done` 的步继续，**不重开目录** |
| `stages["1"].status = done` | 本段已完成 | **一个字都不重做**，念交接话术，退出 |

两个反例：已完成但用户又问「值不值得做」→ 回 S1 **只读不改**（M3 签过，动一字就红）；用户已有确认过的场景表说「接着做」→ 转 02，本段产出场景表，不审别人的。

### 命令

```bash

python3 $SUITE/shared/bin/check_analysis.py --init analysis/<产品>/ --product "<产品名>"
# 进来先看状态（跨会话恢复靠它）
python3 $SUITE/shared/bin/check_analysis.py analysis/<产品>/ --status --stage 1
# 校验：24 条本段 + 6 条跨阶段，全绿才放行

# 算 M3 的 contentHash（写进 confirmations.M3）
python3 $SUITE/shared/bin/check_analysis.py analysis/<产品>/ --hash
```

判据维度、格数、表头一律从 `--spec` 取，不手抄。

### 出口的机读三件

| 字段 | 02 拿它干什么 | 硬约束 |
|---|---|---|
| `p0[]` | 只给 P0 建流程 | 条数等于 M3 的 P0 行数，差一条就红 |
| `roles[]` | 直接映射成契约 `actor`，不另起名 | 每个 id 回指 `M2-roles.md#R-xx` |
| `openQuestions[]` | 只许改 `resolved`/`resolvedBy` | 改正文 → `A-25` 第④重 hash 失配 |

**`p1` 故意不进 export**：P1 已在 M3 的优先级列里，再复制一份就有两份真相。`A-35` 直接从 M3 的 P1 行读，02 逐条给它找下落（进流程或进后置批次并写明理由）。**P1 允许不做，不许没下落。**

### 执行留痕（每步必做）

两层不许合并，都不许手改（只经 `harness.py`）：`_state.json` 记**产物真相**，`_run/` 记**这一轮怎么干的**。完整规则见 `$SUITE/shared/references/08-run-contract.md`，这里只留不能省的五条：

1. **开工先 `next`**：`harness.py next --dir analysis/<产品>/` 打目标原句 + 当前位置 + 下一步 + 三条约束。不许凭记忆说"上次做到 A2"。
2. **每步贴进度块**：`next --brief` 的 3 行**原样贴进回复**，不概括。界面任务列表靠不住，文字才是落点。
3. **有产出才记一步**：算一步＝读材料得出结论 / 写改产物 / 跑校验并解释结果 / 开评审；不算＝纯检索、grep 定位、翻目录。`--intent` 写**判断**不写动作。
4. **完成由产物决定**：`step --done --taskId A2 --out M2-roles.md`，文件必须真存在且 `doneWhen.contains` 的串真出现，否则 exit 6。里程碑自检**只读**，不给任务打勾。
5. **三种异常三种动作**：exit 4 跳步 → 读注入块回正，不重开；exit 3 偏离 → 单次放行、连 3 次才拦，真要加步骤走 `amend --why`；exit 2 循环 → **立刻停，不许换说法重试**，写清卡点交用户。

`blocked` 之后不许自己 `--force-unblock`——死循环之所以发生，就是模型相信"再试一次就对"。

## 三、M3 是唯一的硬闸门：五重

喊「场景没遗漏」不算数，`_state.json` 里要有五样东西（`A-25`）：

| 重 | 字段 | 挡什么 |
|---|---|---|
| ① 有人 | `confirmations.M3.by` 不含 AI/模型/助手/Claude/GPT | 模型替用户签字 |
| ② 有时 | `.at` 是合法 ISO8601 且不在未来 | 时间写未来，mtime 判据恒绿 |
| ③ 有据 | `.quote` ≥4 字，含 `S\d`／维度名／「没遗漏」／≥2 个业务实词 | 用「好的」冒充确认 |
| ④ 对版 | `.contentHash` = M3 去「确认记录」节后的 sha256 前 12 位 | 确认后又偷改场景表 |
| ⑤ 未跳步 | `M4` 不存在，或 mtime ≥ `M3.at` | 先写完第 4 步再回头补签 |

拦下时照这个句式，不要自己找台阶：

> M3 闸门未通过：[哪一重]。场景表共 16 条，P0 6 条，待确认 4 条。
> 请回我一句「场景没遗漏，可以继续」，并确认这 4 条待确认怎么定，我再往下做第 4 步。

穷举只有一个判法：**每个格子都有交代**。82 格由脚本按取值表实时求和（Σ 启用维度的取值数），关一维分母自动变。红线：空格 0、排除 ≤40%、场景 ≥15、P0 ≥5、待确认 ≤7 格。
