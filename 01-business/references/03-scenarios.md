# M3 场景：十一维矩阵与穷举协议

> 这一份是本 skill 的核心。「穷举」不靠灵感，靠**每个格子的归属都有交代**：
> `穷举 = 82 个 (维度, 取值) 格，每格要么是 S 编号，要么是一条含具体事实的排除理由，要么是一条待确认（≤7）。空格数 = 0。`
> 脚本 `A-24` 按本文件的取值表实算总格数，不接受手写。

## 一、十一个维度与取值（逐字，脚本按此校验）

| 维度 | 族名（写进表里的） | 取值（穷举轴） | 格数 |
|---|---|---|---|
| D1 | `阶段` | 创建前 / 创建 / 待处理 / 处理中 / 待确认 / 已完成 / 已作废 / 归档后 | 8 |
| D2 | `触发` | 计划 / 异常 / 手工 / 接口 / 扫码 / 定时 / 导入 / 设备信号 | 8 |
| D3 | `批量` | 单条 / 一批 / 多批混选 / 全量 / 拆批 / 并批 / 分批到货 | 7 |
| D4 | `来路` | 正常入库 / 退货再入 / 让步接收 / 转库调拨 / 委外回收 / 返工返修 / 试制 / 客户供料 / 紧急放行 | 9 |
| D5 | `角色` | 发起 / 执行 / 审核 / 下游等待 / 监管 / 外部方 / 班组长 / 替班 | 8 |
| D6 | `结果` | 通过 / 部分成功 / 全失败 / 超时 / 重复 / 越权 / 数据不全 / 断网 | 8 |
| D7 | `连续` | 编号连续 / 断号 / 重号 / 跨月跨年 / 一物多码 / 多物一码 / 人为改号 | 7 |
| D8 | `版本` | 首建 / 标准换版 / 主数据变更 / 作废重开 / 历史迁移 | 5 |
| D9 | `时间` | 白班 / 夜班 / 交接班 / 峰谷 / 跨天 / 月末 / 停产检修 | 7 |
| D10 | `现场` | 产线 / 工位 / 车间 / 仓库 / 在途 / 无网 / 戴手套 / 噪音 / 光线 | 9 |
| D11 | `形态` | 粉体 / 液体 / 卷材 / 结构件 / 气体 / 其他 | 6 |

> 族名必须是短词：场景与矩阵里写 `族:值`（`现场:无网`），写 `载体与现场条件:无网货场` 一行就占掉半个表格宽度，人写到第三行就开始乱标。

**合计 82 格**（D1~D10 = 8+8+7+9+8+8+7+5+7+9 = 76，+D11 6 = 82）。

> **D4 里故意没有「先入后检 / 先检后入」。** 这两个是结论（谁先谁后），写进词表等于把答案塞进题目——扫出来的是自己的假设，不是从业务里发现的。它们靠 `Step 2.5 跨系统动作时序` 与场景库 `SC-11` 进来。
> **A-24 判据**：取值表里出现结论型取值（`先入后检 / 先检后入 / 先做后审 / 先审后做 / 事后补录`）直接红。本表是唯一源，`DIMS` 必须与 `scripts/check_analysis.py` 的 `DIMENSIONS` 常量逐字一致。

启用规则：
- **核心 6 维（D1~D6）每个业务对象必扫**；
- **扩展 5 维（D7~D11）按对象性质启用**：有编号就启 D7，有标准/主数据就启 D8，跨班就启 D9，不是纯办公室操作就启 D10；
- **D11 `形态` 只对"有物料"的对象启用**，取值从物料主数据的形态字段来。它治的是矩阵外最容易漏的那类场景：电解液效期、隔膜分卷、粉体水分——同一批货形态不同，取样与存储完全是两套做法；
- 制造业项目实际 11 维全开，只有纯后台配置功能才关 `现场`；`形态` 凡有物理形态的对象一律启用。
- 关掉的维度写进 `_gate.json` 的 `matrix.enabledDims`，总格数自动变（例如关 `连续`：82−7=75；再关 `形态`：69）。

## 二、只跑 8 组高危配对（不做全笛卡尔积）

全组合约 1.5 亿，不可执行。真正出事的是这 8 组：

| # | 配对 | 交叉点 | 必须产出的一条场景 |
|---|---|---|---|
| 1 | D4 来源 × D1 阶段 | 来料在「待处理」前是否已入库 | **先入后检 / 先检后入**（用户踩过的坑 1）——由 Step 2.5 问出来，不靠 D4 词表 |
| 2 | D7 连续性 × D3 批量 | 断号时怎么判定该检哪些批 | **按频次抽检但批次号不连续 → 抽检基准失效**（坑 2） |
| 3 | D3 批量 × D5 审核人 | 批量里有一张撞四眼 | 整批退回 / 跳过该张 / 拆两张单 |
| 4 | D9 班次 × D1 阶段 | 单据停在「处理中」时交班 | 交接班未提交单据归谁、算谁的 KPI |
| 5 | D2 触发 × D6 分支 | 设备信号触发但部分成功 | PLC 给 10 条、系统只收 7 条，另 3 条怎么补 |
| 6 | D10 载体 × D6 分支 | 无网 + 提交失败 | 存本机 / 纸记 / 回办公室补录，补录要不要标「补录」 |
| 7 | D8 版本 × D1 阶段 | 换版后看已归档单据 | 按旧版还是新版判、能不能重算 |
| 8 | D5 外部方 × D1 阶段 | 供应商在报告发出前就要结果 | 电话先告知 / 只给结论 / 拒绝 |

第 1、2 组直接来自用户踩过的坑。**扫到就必然产出那条场景**——这是本 skill 对他最值钱的地方。

## 三、五步扫描协议（可机械执行）

```
Step 1 定扫描对象
  从 M1 的原话里抽业务对象（单据/批次/工单/样品/设备），每个对象扫一轮。
  例：来料检验 → 来料批次、检验任务、检验报告。

Step 2 单因子扫描
  固定其余维为「常规值」，把这一维每个取值走一遍，每格问一句：
  「这个取值下，用户会做什么、系统要判断什么？」
  常规值写在矩阵顶部一行备注：来源=正常采购入库、批量=单批、角色=执行人、结果=通过。
  产出：候选场景，先落 _draft/M3-candidates.md。

Step 2.5 跨系统动作时序（每画到一个跨系统交接点必做）
  对每个交接点问三句：
    ① 谁先谁后？（收货先在 WMS 建单，还是检验先在 QMS 建任务）
    ② 反过来行不行？（先后颠倒，业务上是否成立）
    ③ 反过来时，两边单据状态各变成什么？
  来料这条问出来的就是「WMS 收货 vs QMS 检验」的正反两种：
    先检后入（S1）与先入后检（S2）——两条都成立，都得建场景。
  为什么单列这一步：D4 的来路是中性的，先后顺序藏在系统交接里，不在物料来源里。

Step 3 高危配对扫描
  只跑上面 8 组，每组至少 1 条候选。产不出来说明 Step 2 扫太浅。

Step 4 归属裁决（不许留空）
  每条候选二选一：
    进场景表 → 分 S 编号，十字段填满；填不满退回 _draft
    不进场景表 → 矩阵里写「排除」+ 含具体事实的理由
  判断不了 → 写「待确认」并进待确认清单。待确认 ≤7（A-24）。

Step 5 覆盖自检
  总格数 = Σ(启用维取值数)；已归属/总格数 = 100%。
  待确认 ≤7；排除 ≤40%；场景 ≥15，其中 P0 ≥5。
```

## 四、覆盖矩阵怎么写（一件事一行，不许合并）

| 维度 | 取值 | 归属 | 理由 |
|---|---|---|---|
| D4 来源与来路方式 | 先入后检 | S2 | 急用料先进库、判定后补，库存挂待检冻结 |
| D4 来源与来路方式 | 先检后入 | S3 | 常规路径 |
| D7 标识连续性 | 断号 | 排除 | 批次号由供应商提供且要求连续，断号时抽检基准改按收货流水号（M5 第 7 行），不单独成场景 |
| D9 时点与班次 | 交接班 | S7 | 上一班未提交的单据归谁 |

### 排除理由的合格 / 不合格

| 不合格（`A-24b` 判红） | 合格 |
|---|---|
| 不适用 | 本期工艺路线 12 道全在厂内，无委外工序 |
| 业务上不需要 | 作废单不做查询入口，只按单号穿透（M4 第 7 步） |
| 概率低 | 节假日停线不收货，到货预约在 SRM 已关闭 |
| — | 件码由 WMS 在包装环节生成，来料只有托盘码 |

**硬要求**：理由里必须有一个具体事实——数字、系统名、单据名、场景号或步号。理由要能让第三个人复核。

**人工自检（判据拦不住这一条，必须人做）**：写完每条排除，问一句——**如果这件事真的发生了，是哪一格接住它？**
答得出来，就把那个格号写进理由（`D1 待处理 × D6 超时`），下次复核一眼能核；
答不出来，这条排除就是错的。两个真实教训：「创建前」被读成「到货前」，把先入后检这一整个状态排掉了；「油污反光」被读成「不是光线问题」——同一句话在证明光线重要，同时把光线排除了。
这类错误带数字、带引用、`A-24b` 一条都拦不住，因为它不是形式问题，是把状态读错了。

### 结论型取值：不许把答案写进题目

| 反面（写进词表就是作弊） | 正确做法 |
|---|---|
| D4 取值写「先入后检 / 先检后入」 | D4 只写「正常采购入库 / 紧急放行」，先后顺序由 Step 2.5 问出来 |
| D7 取值写「断号导致漏检」 | D7 只写「断号」，漏检后果写进场景与异常 |
| D6 取值写「审批被驳回」 | D6 只写「全部失败」，驳回原因留给场景 |

判断标准一句话：**这个取值换个业务对象还成立吗？** 「断号」对工单、批次、托盘都成立；「断号导致漏检」只对这一次成立，那就是结论。

### 待确认也不是垃圾桶

待确认 ≤7 格，且每一格都要进 M3 的待确认清单，配上「我给的建议」和「你不定会怎样」。M3 确认之后，矩阵里的待确认必须归零：转成 S 编号或转成排除。

## 五、场景表十个字段的写法

| 字段 | 要求 | 反面 |
|---|---|---|
| 场景名称 | 业务动作，不含页面/按钮/弹框/字段/接口/菜单/标签页 | 「检验报告页面」 |
| 触发时机 | 时间或事件（当…/每天/接到…后/换版日/盘点期） | 「需要时」 |
| 用户当前状态 | 手部状态、姿势、信号、光线、噪音 | 「正常」 |
| 用户想完成什么 | 他要的结果，不是他要的功能 | 「使用系统」 |
| 系统应该提供什么帮助 | 具体到交互与默认值 | 「提供查询功能」 |
| 优先级 | P0 阻断生产 / P1 影响效率 / P2 体验 | 全填 P0 |
| 发生频次 | 次/天、次/周、次/月 | 「偶尔」 |
| 失败兜底 | 走不通时他实际会怎么做 | 「提示用户」 |
| 受影响角色 | 谁在等这个结果 | 「相关人员」 |

**关于「报表 / 报告」**：它在制造业是业务对象（客审要报表、月报），不一定是实现名词。`A-21` 的处理是：场景名含「报表/报告」且「用户想完成什么」是交付语义（交/给/审/导出给）时降为 WARN；含页面/按钮/弹框/字段/接口/菜单/标签页仍然直接 ERROR。

## 六、这套矩阵在六步里各用一次

| 步 | 用哪个维度 |
|---|---|
| M1 | D5（谁受损）+ D1（损失发生在哪个阶段）：把「效率低」翻译成「在哪个阶段卡了多久」 |
| M2 | D5 全取值反查角色表——没被任何场景用到的角色是多余的；D9 反查「替班者」在不在表里 |
| M3 | 全 10 维 + 8 组配对（主战场） |
| M4 | D1（阶段=状态集）+ D3（批量粒度列）+ D6（分支流程） |
| M5 | D6（结果分支都要变成异常）+ D7 + D8 + D10 |
| M6 | D10（现场使用者的提问全从这一维来）+ D3（批量出问题最凶） |

做完这一步，M3 的场景表、M4 的状态集、M5 的异常类必须对得上：状态机的每个状态能追到至少一个场景，异常清单每行能追到一个场景或流程步（`A-43`）。追不到的地方，就是这次分析的真实缺口。
