## 案例 1（元级）· 矩阵把自己的答案当成了发现

**现象**
实跑 QMS 来料检验（`_design/DRYRUN-qms-incoming.md`）时，`D4 来路` 的取值表里写着「先入后检」「先检后入」。扫到这两格，矩阵"产出"了用户踩过的第一个坑。覆盖数字很好看：78 格全部有归属、空格 0、排除率 15%。但这两格是自问自答——那两个词是**知道答案之后**才写进词表的。把场景名当成维度取值，扫描就退化成检索：检索只能找到你先放进去的东西。

**根因**
把领域知识塞进了扫描轴。设计词表时的心理动作是「我知道这个项目会出什么事，把它放进取值里，这样一定会扫到」——听起来是求稳，实际是把「验证」换成了「复述」。更隐蔽的是它让所有验收指标同时变好：覆盖率高、空格为零、排除率低。**这是唯一一种"做得越认真、假象越强"的失败**，因为它伪装成严谨。

**修法**
1. 取值只放**中性轴**——时间、空间、形态、数量、顺序的类别。"谁先谁后""该不该检"这类带结论的词一律不许进词表。
2. 结论下沉到两处：场景库（`08-scenario-library.md`，写"长什么样"）与协议（`06-dimensions.md` 的 **Step 2.5 跨系统动作时序**，问"两边单据谁先建、反过来行不行、反过来时各自状态变什么"）。
3. 实跑同时逼出第 11 维 `形态`（粉体/液体/卷材/结构件/气体）：它是真正的中性轴——不预设结论，但能把取样方式、包装、效期、存储条件的差异扫出来。

**判据**
`A-24c`：`DIMS` 常量里任一取值，与本项目场景名的公共子串 ≥4 字即报 ERROR。
造红方式：把 `先入后检` 写回 `D4 来路`，脚本必须报 `A-24c` 并指出它和哪条场景名重合。

**自查动作**（写完词表后逐维做一遍）
把所有取值遮住，只看维度名，问自己一句：**「这个维度名能不能让我问出一个我现在还不知道答案的问题？」** 问不出来的那一维，它的取值就是结论，不是轴。

**造红的边界**（这一条要跟着每一条判据走）
**造红证明判据没死，证明不了判据够用。** 上面那个 `A-24c` 能拦住"词表里写了结论"，却拦不住 `A-24b` 那类问题——三条排除理由都带具体事实、造红也全红，因为它们红的条件是"有没有事实"，而错恰恰出在事实用得对不对。判据只能证明自己还活着；**够不够用，只能拿真需求跑一遍才知道**。

## 案例 2 · 排除理由写的是现状，不是设计

**现象**
矩阵里三格被排除，理由分别是「仓库有 WiFi」「留样到期清理不在本期」「年均 ≤3 单」。三条理由本身都是真的，也都带事实。但前两条后来都收成了场景：`D10 现场 = 无网` 归给 S14（货场只有 2 格 4G，存本机、回来补传、补录件留痕）、`D1 阶段 = 归档后` 归给 S10（客审要 12 个月前的判定依据与限值快照）。

「仓库有 WiFi」回答的是**现在什么样**；矩阵要回答的是**WiFi 断了怎么办**。仓库确实有 WiFi，所以这句话真的；但它不能替"断网"这个场景做决定。同理，"留样到期不在本期"回答的是"这次做不做清理"，而那一格问的是"12 个月前的报告按哪版限值看"——两件事。

**根因**
把环境当约束。写排除时，人本能去找"我们已经有 X 了"这类事实——它好写、可核实、听着还专业。而"X 失效时怎么办"要想清楚才有答案，还容易当场暴露设计缺口。于是排除理由退化成现状陈述，**缺口被现状挡住了**：不是想清楚之后排除的，是找到一句真话之后就不用再想了。

这是"拿事实包装判断"的第二种形态。第 1 条案例是自己骗自己（把答案写进输入），这一条是**用环境的现成答案替设计做决定**。

**修法**
排除理由只接受三类，写不出第三类就说明该改成场景：

| 允许的排除理由 | 写法 |
|---|---|
| 由别的格承载 | 直接写格号：`超期由 D1 待处理 × D6 超时 承载` |
| 本项目客观不存在 | 带数：`客供料 0 批`、`形态未登记物料 0 类` |
| 不属于本系统 | 指名：`转库由 WMS 内部完成`、`在途运输在 SRM` |

凡是出现「我们有 X」「我们的流程一直是」「平时都正常」，一律先追问一句：

> **X 坏了、或者 X 没有的时候呢？**

答得出承接方案的，改成场景；答不出的，才是真正的排除——但这时你手里已经有一条设计原则（比如"离线可继续录入、恢复后补传、补录件留痕"），它比排除本身值钱。

**判据**
`A-24b` 只能验形（这条理由里有没有具体事实、数字、系统名），验不了「这条事实该不该用来做排除决定」——上面三条理由全都带事实，全绿。

这一条靠人工，问句是：**这条理由说的是现状，还是应对？**

**这条的病根，判据侧拦得住：同一件事写两处，必然漂**

上面是"判断错了"，脚本拦不住；但它暴露的机制是另一回事——**凡是同一件事被写在两个地方，早晚有一处会忘**。这条机制能靠判据掐死，而且比"比对一下至少能拦写错"更彻底：

| 现象 | 判据落点 |
|---|---|
| `decision` 里复述条数（「场景表 16 条」），场景后来加到 19 条却没回头改 | `A-25e`：`confirmations[*].decision` 里命中业务计数主体（`原话/角色/场景/流程/异常/风险/P0` + `N 条`）即 **WARN**；**全文所有命中都报**，不只最后一个 |
| `_gate.json.openQuestions` 的 `text`/`suggest` 与 `M3 待确认清单` 各写一遍，只改了答案没改问题 | `A-25d`：同号行**逐字相等**，两边条数也要对齐，不一致即 **ERROR** |

**`A-25e` 故意不比对数字，只禁止写第二处。** 比对只拦"写错"；拦不住"当时写对了，后来改场景忘了改 decision"——后者才是真会发生的。条数只该活在 `steps[].rows`，一处源。

同理，`openQuestions` 不再手抄，由脚本从 `M3 待确认清单` 读表回填。

## 案例 3（元级）· 判据能验形，验不了义

**现象**
为了让 `A-63` 拦住「02 写了页面怎么画」，有人提议把中文「组件树」也加进越界词表。动机没错——02 的产物里确实不该出现页面结构。但词表加上「组件树」的那一秒，`M4` 里这句就被判红了：

> 页面组件树与交互由第 3 段补，本段只给页面骨架。

这恰恰是我们**最想让 02 说**的一句话。实测对照：

| 输入 | 应判 | 实际 |
|---|---|---|
| `页面组件树与交互由第 3 段补` | 放行 | 加中文词后 → 红（错杀） |
| `componentTree 按状态拆三块` | 红 | 红（正确） |

**根因**
把「提到」当「写了」。词表只能装**结构键名**（`componentTree` / `ui.kind` / `pages[].prd`），装不进自然语言——中文里同一句话既可能是越界，也可能是正确的交接说明，字面上分不开。这不是词表漏了词，是**词表这种机制本身验不了义**。

同类已经出现四次，都是「形对了、义不对」：

| # | 判据 | 验得住（形） | 验不住（义） |
|---|---|---|---|
| 1 | `A-24c` | 词表里有没有结论型取值 | 造红只能证明判据活着，证明不了够用（案例 1 §造红的边界） |
| 2 | `A-24b` | 排除理由里有没有具体事实 | 这条事实该不该用来做排除决定（案例 2） |
| 3 | `L2-34` | `acceptance` 里有没有一条 `kind:"illegal"` | 这条非法路径与状态机是否真冲突（实测：编一条也能过） |
| 4 | `A-63` | md 里有没有渲染层**键名** | 中文是不是在讨论渲染层（本案例） |

**判据侧能做的**
只认键名与 JSON 结构。**词表里每加一个中文词，就必须能举出一个「正确但会被误伤」的句子**——举不出来才加；举得出来就说明这个词不该进表。加中文词等于逼人换说法（「渲染那部分交给下一段」），判据立刻形同虚设。

**人侧要做的**
读 02 的产物时，看 `pages[]` 里有没有 `componentTree` 键，**不看正文怎么描述**。判断"02 越界了"的证据是结构，不是措辞。

**造红用例选错了，不是判据漏了**
写这条案例时先入为主地写了个「中文该红」的用例，跑出来不红，第一反应是"判据有洞"。实际是**用例本身错了**。顺序应是：

> **判据红的第一次，先怀疑样例，再怀疑判据。**

同一轮里 `A-35` 就是这么发现的：新判据一上，`qms-incoming` 红在 7 个 P1 无下落——不是判据太严，是样例真缺了「后置批次」这一节。补完样例转绿，判据一个字没改。

## 案例 4（元级）· 报告说改了，成品没改

**现象**
三段式重组里撞了三次，形态一模一样：
1. 说「`export.p1` 已删」，`02-requirement/SKILL.md:37` 还留着——因为 02 是从旧副本建的，01 那份清干净了，02 没有。
2. 说「签署点统一」，`A-36` 那行改成了 M6，同文件另外三处（卡点、S6、references 索引）仍写 A2/A3。
3. 我给的口径写 `confirmations.A2.at`，而新的 schema 里根本没有 `A2` 这个键——**照着自己写的文档去实现，第一步就 KeyError**。

**根因**
和案例 1 同构：把「我做过」当成「它发生了」。三份 SKILL.md + 共享 references 是同一批事实的多份副本，改动靠人记住改哪几份；而验收看的是**提交信息与 diff 说明**（它们由改的人写，当然说改好了），不是**成品的当前内容**。

**修法**
1. 凡「删某个字段 / 改某张表 / 统一某个叫法」，验收动作固定为**在成品里 grep 那个字符串**，不是读 diff、不是读提交信息。
2. 一条事实只允许存在一处，其余靠引用——`export` 收回 `p1`、P1 清单改从 M3 的优先级列读，就是这个修法的产物。副本越多，这一条越容易踩。
3. 提交信息不写「已改 X」，写「`grep X` 无输出」。

**判据**
这一类没法靠 `check_analysis` 抓（它读 md 判形，不判"两份副本是否一致"），只能靠命令。**注意范围要限定在活文件**——本案例正文自己就引用着这两个错串，`grep .` 必然命中自己：
```bash
grep -rn "export\.p1\|confirmations\.A2" 0*/SKILL.md shared/bin shared/schemas examples   # 必须无输出
grep -c "name: iiot-" */SKILL.md                                                         # 每份 1 行
```
造红方式：把 `export.p1` 写回任意一份 SKILL.md，第一条命令必须出结果。**说不出 grep 命令的那次改动，等于没验收。**

**自查动作**
每次说「改完了」，先问自己：**这条改动，我能给出一条现在跑、结果为空/为真的命令吗？** 给不出，就还没改完——只是写了。

### 案例 4 之二 · 加一个分支，旧文案就变假

同一族的第二个形态，但**它 grep 不出来**。

`A-68` 的报错文案原先写着「在那之前 A-67 对渲染键只报 WARN，不构成闸门」。写这句话时 A-67 只有两种分支（无签收 / 有签收未变），这句话在两种上都成立。后来给 A-67 加了第三种分支（md 变了 → 签收失效 → ERROR），这句话在新分支上**就是假的**：md 一变，A-67 恰恰是闸门。

代码改了、文案没改。但没有任何 grep 能查出来——字符串本身没被改"错"，它是被新增的分支**变**错的。

**根因**：把「文案」当成了「注释」。注释只描述写下它的那一刻，文案要覆盖它出现的每一个分支。加分支时人只想着新分支的代码，不会回头读旧分支的字符串。

**修法**：
1. 文案里出现「只」「都」「不构成」「永远」「一律」这类**全称判断**的，加分支时必须重读；
2. 更硬的一条：**文案不要描述别的判据的行为**。`A-68` 说「A-67 不构成闸门」本身就错了——它该说的是自己「契约已过期，需重出重签」；A-67 会不会红是 A-67 的事，跨判据的承诺必然腐烂。

**自查动作**（加分支时做，不是写完时做）：
把本判据已有的每一条 `add(E/W, ...)` 文案逐句读一遍，问：**这条文案在我刚加的那个分支上还成立吗？**

## 案例 5（元级）· 判据的白名单要拿全量样例反推，不许凭脑子正推

**现象**
`A-67`（02 只许交语义半边）第一版白名单，照「02 该写什么」正推出来 12 个顶层键、8 个页面键。落实现后立刻三个错：

1. 顶层漏 `stateMachines`/`guards`/`modules`/`dataModel`/`dataSources`/`openQuestions`——写成单数 `stateMachine`，还编了一个 schema 里不存在的 `businessRules`；
2. 页面项漏 `contract`——而 `contract.owns` 是「这页负责哪些命令」，`L2-21`/`L2-81`/`L2-91` 全靠它，漏了 02 连命令归属都交不出来；
3. 命令项漏 `label`——`L2-52` 明令「命令必须有用户可见动作名」，`A-67` 却说「写了就错」。**两条判据当场打架。**

三次都不是手误，是同一种动作：**坐在那儿想"02 应该写什么"，而不是去看"02 实际写了什么"。**

**根因**
白名单是**关于既有事实的断言**，不是设计意图。凭意图写，写出来的是"我希望 02 写什么"，而判据要卡的是"02 实际能写出什么"。两者差多少，只有全量样例能告出来——单看自己造的那一份不够，它本身就是照意图造的，两边一起错还互相印证。

**修法**
1. 白名单**从产物反推**，一条命令就能拿全：
   ```bash
   python3 -c "
   import json,glob
   ks=set(); pk=set()
   for f in glob.glob('**/*.proto.json',recursive=True):   # 指你的契约目录
       d=json.load(open(f))
       for c in d.get('capabilities') or []: ks|=set(c.keys())
       for p in d.get('pages') or []: pk|=set(p.keys())
   print('caps:',sorted(ks)); print('pages:',sorted(pk))"
   ```
   顶层键则以 `shared/schemas/proto.schema.json` 的 `properties` 为准，不以任何人的记忆为准。
2. **样例反推完之后，再拿每条 `L2` 的必填项反查一遍。** 样例覆盖不到的必填项，只有判据清单里有——`label` 就是这么漏的：四个样例里都有 `label`，但它不显眼，第一版白名单照"02 该写什么"想的时候漏了，结果 `L2-52`（命令必须有用户可见动作名）与 `A-67`（写了就错）当场打架。**"新判据把老判据的合法输入判成非法"，比单纯漏键更难发现**，因为两条判据各自看都对。
3. **写完先跑一遍全部样例**，不只跑自己造的那一份；再跑一遍 `--half req` 的正向基线——白名单与"必须有"型判据打架，只会在正向基线上暴露（`L1-01` 要 `components` 存在、`A-67` 说非空即红，两者能同时成立的前提是"允许空数组"，这一点也是跑出来的）。
4. **一个永远算不出真值的字段，比没有这个字段更危险。** `derive()` 曾给第 3 段算了个 `status`，但第 3 段没有对应的 M 文件，于是它恒为 `pending`。后面两拨人（包括我自己）都照着它写 `if status == "done"`，写出来的是恒假分支——**判据看起来在，实际一行没跑**。现在 `stages` 只建 1 和 2，第 3 段的状态一律由产物推断并如实打印（未构建 / 已构建 / 产物过期），不编。

5. 判据之间**不许互相矛盾**：一条说"必须有"，另一条不许说"写了就错"。发现矛盾先改白名单，不要改另一条判据去迁就它。

**为什么值得单独记**
这条和案例 1 是同一台机器的两面：案例 1 是把自己的答案写进输入再扫出来，这条是把自己的意图写进判据再拿去卡产物。**两者的共同症状都是"第一次跑就全绿或全红"**——全绿说明判据没碰到真东西，全红说明判据在打合法写法。

## 新增案例的准入

只收「能在 M1~M6 里指到一个具体缺口」的案例。写不出「当时多做哪一步」，那是抱怨不是案例，不收。

## 怎么用

1. 项目开始前，按业务域筛出相关的 5~7 条，对着看自己的矩阵有没有扫到对应格子。
2. 分析做完后，拿这 17 条业务坑当回归清单（案例 1~5 是方法级，用来自查怎么做的，不对应具体格子）：任何一条在本次分析里「能对应到某个格子的缺口」，说明还没穷举完。
3. 遇到新坑，先判断它属于哪一步、哪一维，再补进来——不加维度，只补现象与归因。> **脚本对应判据**：`A-24` 的结论型取值守卫（`CONCLUSION_VALUES`）——取值表里出现 `先入后检/先检后入/先做后审/先审后做/事后补录` 直接红。
